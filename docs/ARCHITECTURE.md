## 2. Принципы

Порядок приоритетов при конфликте ([ADR-0001](ADR/0001-design-principles.md)):

1. Корректность безопасного подмножества.
2. Простая и единая модель.
3. Предсказуемая производительность.
4. Удобство чтения и написания кода.
5. Скорость компиляции и отзывчивость инструментов.

**Правило объёма:** возможность попадает в 1.0, только если она нужна нише 1.0 и может быть доведена до качества релиза. Остальное — после 1.0, но так, чтобы её добавление не требовало перестройки.

## 3. Границы KENOX 1.0

### 3.1 Три опоры

**1. Безопасное ядро языка**
- Типы: `struct`, `enum` с данными, трейты, обобщения (мономорфизация), `dyn Trait`, кортежи, массивы, срезы, строки, простые константные параметры обобщений.
- Владение, ссылки второго класса, RAII, `Result` и `try`, `T?` как `Option<T>` с `?.` и `?:`.
- Замыкания (невыходящие по умолчанию), итераторы, сопоставление с образцом, перегрузка операторов через трейты.
- Удобство: `val`/`var`, функции-выражения, строковые шаблоны `"{x}"`, именованные аргументы и значения по умолчанию, trailing-лямбды, `extend`, `@derive`, `is` и `if val` с привязками.
- Простые `const fun`.

**2. Системная интеграция и производительность**
- Полноценный C ABI: импорт, экспорт, статические и динамические библиотеки, генерация C-заголовка ([ADR-0013](ADR/0013-ffi.md)).
- `unsafe`, сырые указатели, Allocator API, арены, `Shared`/`Weak`.
- Потоки, `Send`/`Sync`, синхронизация, каналы, пул потоков, параллельные итераторы.
- Портируемые SIMD-типы, контроль раскладки и выравнивания.
- Профили Debug, Release, Performance, Size с LTO.

**3. Инструменты**
- Компилятор с качественной диагностикой.
- `kenox build`, `run`, `test`, `fmt`, `check`.
- Простой пакетный менеджер: зависимости по пути и из git, lock-файл.
- Базовый LSP: диагностика, переход к определению, типы при наведении.
- Отладочная информация для отладчиков ОС.

### 3.2 Что входит в 1.0 и что нет

| В 1.0 | После 1.0 (1.x) | Не планируется |
|---|---|---|
| Ядро языка (опора 1) | async/await и структурированные async-задачи — 1.1 (принято, [ADR-0005](ADR/0005-concurrency.md)) | Наследование реализации |
| C ABI, библиотеки, генерация заголовков | `class` — ссылочный тип-сахар над `Shared` | Специализация реализаций, HKT |
| Потоки, синхронизация, каналы, пул, параллельные итераторы | WebAssembly (WASI и браузер) | Неявные преобразования типов, перегрузка функций по типам |
| SIMD-типы, выравнивание | Android (библиотека через NDK и JNI), затем iOS | `comptime` в стиле Zig |
| `Shared`/`Weak`, арены, Allocator API | PGO, быстрый backend для Debug, инкрементальная компиляция | GUI-фреймворк в стандартной библиотеке |
| `const fun`, встроенный `@derive` | Импорт C-заголовков (если не успеет к 1.0); генераторы привязок для Kotlin, Swift, C++ | Стабильный ABI между версиями KENOX (кроме C ABI) |
| `kenox` build/run/test/fmt/check, пакеты из git, базовый LSP | Реестр пакетов; макросы или статическая рефлексия | |
| Tier 1: Linux x86_64 и aarch64, macOS aarch64, Windows x86_64 | Исследование GC при условиях [ADR-0026](ADR/0026-gc-readiness.md) | |

### 3.3 Синтаксис

Основа — Kotlin (`fun`, `val`/`var`, `имя: Тип`, trailing-лямбды, `?.`, `?:`), но синтаксис собственный: каждое отличие решает конкретную задачу системного языка с владением ([ADR-0010](ADR/0010-syntax.md), [эскиз](SYNTAX_SKETCH.md)). Пример из корпуса:

```kenox
fun deposit(inout account: Account, amount: Int) {   // изменяемое заимствование
    account.balance += amount
}

fun close(consume account: Account): Int {           // передача владения
    println("счёт {account.owner} закрыт")
    return account.balance
}

var acc = Account(owner = "Анна", balance = 100)
deposit(&acc, 50)        // `&` — на месте вызова видно, что аргумент изменяется
val rest = close(acc)    // дальше `acc` недоступна — это проверяет компилятор
```

Корпус из 44 примеров выявил и помог устранить три конфликта, которые сделали бы язык противоречивым: `?` против `?.` (передача ошибки — `try`), фигурные скобки как блок или замыкание (блок — `do { }`), тип строкового литерала (`String` без выделения памяти). Подробно — [CORPUS_REVIEW.md](CORPUS_REVIEW.md).

## 4. Модель памяти

Решение принято ([ADR-0002](ADR/0002-memory-model.md)): **единственная модель — владение; механизмы — разные виды владельцев.** Поэтому они не конфликтуют во время выполнения.

| Механизм | Роль в 1.0 | Где описан |
|---|---|---|
| Владение, перемещение, RAII (`Drop`) | Основа: память и ресурсы освобождаются детерминированно | ADR-0002; аудит §5.2 (M1, M6) |
| Ссылки второго класса | Доступ без копирования; режимы параметров `inout` и `consume` | [ADR-0003](ADR/0003-borrowing-model.md) — предварительно принято |
| Арены и Allocator API | Массовое выделение и освобождение; связи — дескрипторы `Id<T>` | ADR-0002; аудит §5.2 (M4) |
| `Shared`/`Weak` | Данные с несколькими владельцами | ADR-0002; аудит §5.2 (M3) |
| `unsafe` | Вызов C, реализация std, низкоуровневые операции | Аудит §5.2 (M5) |
| Трассирующий GC | Нет в 1.0; путь к нему сохранён | [ADR-0026](ADR/0026-gc-readiness.md) |

**Гарантии безопасного кода** (ваше условие от 05.11): нет некорректного доступа к памяти, использования после освобождения и гонок данных. Механизмы — таблица в [ADR-0003](ADR/0003-borrowing-model.md); где это видно в примерах — раздел 4 [отчёта по корпусу](CORPUS_REVIEW.md). Как и в Rust, модель не обещает отсутствия утечек при циклах `Shared`, взаимоблокировок и паник.

**Почему `Shared`/`Weak` остаются, хотя их нет в исходном списке.** Это не отдельный режим памяти, а библиотечный тип поверх владения. Без него нельзя разделить данные между потоками сервера (конфигурация, кэш, пул соединений) и нельзя построить граф с несколькими владельцами. В Rust ту же роль играют `Arc` и `Rc`. Цена — один библиотечный тип и правило «циклы разрываются через `Weak`»; сам язык от этого не усложняется.

**Детерминированное управление ресурсами** — это RAII плюс явный `close(): Result` для ресурсов, закрытие которых может завершиться ошибкой (аудит §5.2, M6). Отдельный Resource Engine не нужен.

**Готовность к GC** ([ADR-0026](ADR/0026-gc-readiness.md)) — восемь ограничений, которые соблюдаются с первого дня. Главные из них:
- безопасный код не опирается на гарантированный вызов деструктора (утечки безопасны);
- будущая GC-куча — отдельный регион со своим типом указателя, а не свойство любого типа; туда допускаются только типы без деструкторов и без заимствований;
- в KIR виды указателей (владеющий, `Shared`, `Weak`, сырой, заимствование) сохраняются до кодогенерации — вид «GC-указатель» можно будет добавить без изменений фронтенда;
- корни будущего GC — через явные дескрипторы, без сканирования стека (это работает и в WebAssembly);
- стандартная библиотека не использует GC-типы в публичных API — GC останется необязательным.

## 5. Конкурентность и параллелизм

**В 1.0** ([ADR-0005](ADR/0005-concurrency.md), принято):
- потоки ОС; автотрейты `Send`/`Sync`;
- структурированные потоки: дочерние потоки заимствуют данные родителя (приём `thread::scope`, проверенный в Rust);
- `Mutex`, `RwLock`, условные переменные, атомики (модель памяти C++20);
- каналы, пул потоков, параллельные итераторы для вычислений.

**Серверы в 1.0** работают на пуле потоков и блокирующем I/O. Этого достаточно для инструментов, внутренних сервисов и умеренной нагрузки [оценка]. Десятки тысяч одновременных соединений требуют асинхронного I/O.

**async/await — в 1.1** (ваше решение от 05.11). Async-runtime на первых этапах не создаётся. Чтобы async добавился без переработки, в 1.0 закладывается:
- **компилятор:** анализ «что живо в какой точке» на KIR (он нужен и для проверки заимствований); трансформации KIR — независимые проходы, поэтому async станет ещё одним проходом «кадр функции → конечный автомат»;
- **система типов:** автотрейты `Send`/`Sync` и невыходящие типы — ими же выражается безопасность кадров задач; ключевые слова `async` и `await` зарезервированы;
- **модель памяти:** невыходящее значение нельзя «потерять» без деструктора — основание для безопасного заимствования данных родителя в дочерних задачах;
- **std и runtime:** блокирующие API ввода-вывода оставляют место для асинхронных версий рядом; потоки создаются через runtime std — точка регистрации для будущего исполнителя есть.

Полная таблица — в [ADR-0005](ADR/0005-concurrency.md). Проверка, что решения этапов 1–2 не нарушают эти условия, — в точке G2.

## 6. Вычисления в 1.0

**Входит:** вычисления на CPU одной машины.
- Портируемые SIMD-типы (`Simd<T, N>`), отображаемые на векторные типы LLVM; функции с явными возможностями процессора.
- Параллельные итераторы по срезам на пуле потоков.
- Контроль раскладки и выравнивания (например, выравнивание по кэш-линии).
- Явные операции заворачивания и насыщения. Ловушка переполнения по умолчанию может мешать векторизации целочисленных циклов — это измеряется (эксперимент E-3).
- Итерация без проверок границ там, где их доказывает итератор; непроверяемый доступ — только в `unsafe`.
- `noalias` для параметров `inout`: исключительное заимствование гарантирует отсутствие псевдонимов, и LLVM может оптимизировать смелее. Включается только после формализации модели алиасинга (ADR-0014, до 1.0).

**Не входит:** GPU; распределённые вычисления (MPI); ослабленная математика с плавающей точкой по умолчанию (возможна как явная опция после 1.0); многомерные массивы в std (это пакет).

## 7. Взаимодействие с C (FFI)

Слои ([ADR-0013](ADR/0013-ffi.md)):

| Слой | Что даёт | В 1.0 |
|---|---|---|
| Язык | `extern "C"` для импорта, `@export` для экспорта, `@repr(C)`, указатели на функции C, строки C, проверка C-совместимости типов на границе; паника на границе — аварийное завершение | Да |
| Сборка | Артефакты: исполняемый файл, статическая и динамическая библиотека; подключение нативных библиотек в `kenox.toml`; позже — сборка C-исходников пакета (Q-41) | Да |
| Инструменты | Генерация C-заголовка по экспортированному API | Да |
| Описание API | Компилятор выдаёт машиночитаемое описание экспортированного API; генератор заголовков работает поверх него | Да (версия 0) |
| Импорт C-заголовков | Отдельный инструмент на libclang, генерирующий объявления KENOX | Если успеет; иначе 1.x (Q-37) |
| Другие языки | Генераторы для Kotlin/JNI, Swift, C++, Python поверх описания API | После 1.0 |

Ключевая идея расширяемости: **генераторы привязок к другим языкам работают не с компилятором, а с описанием API.** Новый язык — новый генератор, без изменений компилятора.

Корпус добавил два уточнения: указатель из `CString` — невыходящее представление, поэтому висячий указатель от временной строки становится ошибкой компиляции (Р-23); значения перечислений из C принимаются как целые и проверяются (Р-24).

## 8. Задел для GUI (без реализации в 1.0)

GUI после 1.0 потребует того, что закладывается уже сейчас:
- обратные вызовы из C в KENOX с пользовательскими данными — FFI 1.0;
- типы, привязанные к потоку (не `Send`), — для объектов, которые можно трогать только из главного потока;
- `Shared` + `Weak` + внутренняя изменяемость — для графов UI-объектов с наблюдателями;
- RAII — для окон и ресурсов GPU;
- однопоточный исполнитель async (1.1) — для интеграции с циклом событий UI;
- динамические библиотеки — для встраивания в существующие UI-приложения.

Если трассирующий GC когда-нибудь понадобится, то, вероятнее всего, ради UI: графы объектов с циклами — его главный сценарий. Корпус это подтвердил: самый громоздкий пример — граф наблюдателей (09-05, Р-20). Поэтому ADR-0026 и стратегия GUI будут пересматриваться вместе.

## 9. Компилятор

Конвейер прежний (аудит §4.1): Lexer → Parser (CST) → AST → разрешение имён → HIR → проверка типов → KIR → проверки владения и заимствований → расстановка деструкторов и мономорфизация → кодогенерация.

Изменения ([ADR-0006](ADR/0006-compiler-architecture.md), [ADR-0027](ADR/0027-ai-assisted-development.md)):

1. **Backend v0 — текстовый LLVM IR + clang.** Компилятор пишет файл `.ll` и вызывает clang, который оптимизирует, компилирует и линкует. Сам компилятор остаётся программой на чистом Rust: собирается `cargo build` на любой ОС без библиотек LLVM. Вывод читаем и человеком, и ИИ. Цена: текстовый формат LLVM IR официально не обратно совместим между версиями, хотя меняется редко [факт], поэтому поддерживаемый диапазон версий clang фиксируется и проверяется в CI (E-8). Встроенный LLVM через библиотеку (backend v1) — до 1.0, только если понадобится: например, ради скорости компиляции.
2. **Эталонный интерпретатор KIR — с первой вехи.** Каждая тестовая программа выполняется дважды — интерпретатором и в машинном коде, — и результаты сравниваются. Это главный автоматический способ ловить ошибки кодогенерации в коде, написанном ИИ. Позже тот же интерпретатор вычисляет `const fun` и проверяет неопределённое поведение в `unsafe`-коде.
3. **Текстовые дампы каждого IR** (`--dump=ast|hir|kir|llvm`) в стабильном формате — для отладки и snapshot-тестов. Вывод не зависит от ОС: окончания строк LF, пути — относительные, с `/`.
4. **Отдельный крейт `kenox_abi`** — правила вызова C для каждой платформы. Его используют кодогенерация и инструменты FFI.
5. **Трансформации KIR — независимые проходы** с общим анализом «что живо в какой точке»: на нём строятся проверка заимствований, расстановка деструкторов, а в 1.1 — преобразование `async fun` в конечный автомат (§5).

Структура крейтов — как в аудите (§4.4) плюс `kenox_abi`; `kenox_interp` переносится из этапа 2 в этап 1.

## 11. MVP (0.1) — уточнённые границы

**Входит:**
- функции; `struct`, `enum` с данными; `match` с проверкой полноты;
- кортежи, массивы фиксированной длины, срезы, `String`/`str`;
- модули (файл = модуль);
- обобщения с ограничениями трейтами (статическая диспетчеризация, мономорфизация), реализации трейтов через `extend`;
- `Option`, `Result`, `try`; `for` по итераторам;
- владение, перемещения, `Copy`, `clone`, `Drop`;
- ссылки второго класса: `inout`, `consume`, `ref`, возврат с выводимой зависимостью;
- `unsafe`, сырые указатели, вызов функций C;
- строковые шаблоны;
- `kenox build`, `run`, `test`; эталонный интерпретатор; диагностика с кодами ошибок.

**Не входит** (этапы 2–4): замыкания, `dyn`, `Shared`/`Weak`, арены, расширения чужих типов, сахар `?.`/`?:`, `const fun`, `@derive`, экспорт в C и сборка библиотек, потоки, форматтер, LSP, пакеты.

**Платформы MVP:** Linux x86_64 и Windows x86_64 (MSVC).

**Вехи и критерии готовности** — [ROADMAP.md](ROADMAP.md), этап 1.
