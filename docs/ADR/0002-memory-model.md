# ADR-0002. Модель памяти

- **Статус:** принято 2026-11-04
- **Дата:** 2026-11-04 (версия 2)
- **Связано:** [ADR-0003](0003-borrowing-model.md), [ADR-0005](0005-concurrency.md), [ADR-0026](0026-gc-readiness.md); [ARCHITECTURE.md](../ARCHITECTURE.md) §4; аудит §3.1, §3.2, §5; вопросы Q-08, Q-09, Q-19–Q-22, Q-32

## Проблема

Исходная концепция предлагала пять механизмов как равноправные части гибридной модели: владение и заимствование, трассирующий GC, арены, unsafe-режим, Resource Engine.

Трассирующий GC рядом с владением создаёт шесть конфликтов (аудит §3.1): разделяемая изменяемость, деструкторы против финализаторов, поиск корней, перемещение объектов против заимствований и FFI, safepoint во всех потоках, раскол экосистемы. Он увеличивает runtime и осложняет WebAssembly, где программа не может сканировать свой стек. Resource Engine дублирует RAII и нужен только потому, что ресурсами может владеть GC.

## Возможные варианты

- **А.** Все пять механизмов — равноправные режимы.
- **Б.** GC по умолчанию, владение — по желанию (модель C# со `Span` и `ref struct`).
- **В.** Владение по умолчанию, GC как тип `Gc<T>` (как Alloy для Rust).
- **Г.** Владение + подсчёт ссылок (`Shared`/`Weak`); арены и `unsafe` — библиотечные механизмы поверх владения; RAII для ресурсов.
- **Д.** Регионы, у каждого своя стратегия управления памятью (Project Verona, кучи акторов в Pony).

## Рекомендуемое решение

Вариант **Г**:

- Единственная модель — владение. Механизмы — разные виды владельцев: локальная переменная, коллекция, `Shared`, арена.
- Разделяемое владение — `Shared<T>` и `Weak<T>` (подсчёт ссылок). Изменение через `Shared` — только через типы с внутренней изменяемостью (`Cell`, аналог `RefCell`, `Mutex`, атомики).
- Арены — библиотека поверх Allocator API; связи между объектами арены — дескрипторы `Id<T>`.
- `unsafe` — локальные блоки; глобальных режимов нет.
- Ресурсы — RAII (`Drop`); для закрытия, которое может завершиться ошибкой, — явный `close(): Result`.
- Трассирующий GC — вне 1.0. Ограничения, сохраняющие путь к нему, — [ADR-0026](0026-gc-readiness.md).

**Решение инициатора (04.11.2026):** отказаться от трассирующего GC в 1.0, сосредоточиться на владении и заимствованиях, RAII, аренах, детерминированном управлении ресурсами и контролируемых низкоуровневых операциях; сохранить возможность добавить GC позже; если более простая модель достаточна — выбрать её.

**Почему `Shared`/`Weak` входят в модель, хотя их нет в этом списке.** Это не отдельный режим памяти, а библиотечный тип поверх владения. Без него нельзя разделить данные между потоками сервера (конфигурация, кэш, пул соединений) и нельзя построить граф с несколькими владельцами. Язык от этого не усложняется.

## Причины выбора

- Механизмы не конфликтуют во время выполнения: все они — формы владения.
- Освобождение памяти и ресурсов детерминировано.
- Маленький runtime: нет потоков GC, safepoint, карт стека, барьеров.
- Подсчёт ссылок работает в линейной памяти Wasm без теневого стека.
- Модель проверена практикой: Swift, `Rc`/`Arc` в Rust, ARC/ORC в Nim.
- GC не решает главную трудность — разделяемую изменяемость. Её всё равно пришлось бы решать типами с внутренней изменяемостью.

## Последствия

- Пользователь должен понимать циклы ссылок и разрывать их через `Weak`. Нужен детектор утечек в отладочной сборке.
- Чтобы `Shared` был быстрым, нужно удаление лишних операций счётчика на уровне KIR (этап 4, по данным измерений).
- Стандартная библиотека проектируется без GC — это совпадает с нишей 1.0.
- WasmGC не нужен; один backend для всех целей.

## Риски

- **Приложения с богатыми графами объектов** (модели UI, редакторы) окажутся неудобными. Снижение: корпус примеров на этапе 0; повторная оценка после этапа 2; путь к GC сохранён (ADR-0026).
- **Стоимость атомарных счётчиков** в многопоточном коде. Снижение: неатомарный вариант для данных одного потока; измерения (Q-09, эксперимент E-2).
- **Арены на дескрипторах** окажутся недостаточными для задач вроде компиляторов. Снижение: эксперимент E-7; запасной путь — регионные ссылки (Q-19).

## Статус и условия пересмотра

Принято. Вопрос о трассирующем GC пересматривается не раньше конца этапа 2 и только по данным измерений (условия — аудит §5.6 и ADR-0026).
