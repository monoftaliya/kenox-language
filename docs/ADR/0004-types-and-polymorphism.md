# ADR-0004. Пользовательские типы и полиморфизм

- **Статус:** предварительно принято для этапа 0 (05.11.2026)
- **Дата:** 2026-11-04 (версия 2 — 2026-11-05, после корпуса примеров)
- **Связано:** [ADR-0002](0002-memory-model.md), [ADR-0008](0008-compile-time-and-metaprogramming.md), [ADR-0010](0010-syntax.md); [ARCHITECTURE_REVIEW.md](../ARCHITECTURE_REVIEW.md) §2.1, §3.7; [CORPUS_REVIEW.md](../CORPUS_REVIEW.md); вопросы Q-06, Q-13, Q-25, Q-26

**Условие инициатора (05.11.2026):** вместо наследования реализации — композиция, интерфейсы и трейты, но с удобными механизмами повторного использования кода.

## Проблема

Предложены Struct, Class, Enum, Interface, Trait, Generics, Extension Functions и Generic Specialization.

- Interface и Trait описывают одно и то же — контракт типа.
- Class с наследованием реализации и обобщениями резко усложняет систему типов: вариантность, хрупкий базовый класс, четыре оси разрешения методов вместе с трейтами и расширениями.
- «Generic Specialization» смешивает два разных понятия: мономорфизацию и специализацию реализаций.

## Возможные варианты

1. Полный набор: классы с наследованием, интерфейсы и трейты (Kotlin + Rust).
2. Модель Rust: `struct`, `enum`, `trait`; классов нет.
3. Модель Swift: `struct` (значение), `class` (ссылка с подсчётом ссылок и наследованием), `enum`, протоколы.
4. `struct` + `enum` + `trait` сейчас; `class` позже — как ссылочный тип с подсчётом ссылок без наследования реализации.

## Рекомендуемое решение

Вариант **4**:

- **`struct`** — значение с владением. **`enum`** — алгебраический тип, заменяет закрытые иерархии классов. **`trait`** — единственное понятие интерфейса: методы, методы по умолчанию, ассоциированные типы, статические функции; реализуется для любых типов при соблюдении когерентности (Q-13).
- **Полиморфизм:** обобщения с ограничениями (статическая диспетчеризация, мономорфизация) и `dyn Trait` (динамическая).
- **Специализация реализаций** (перекрывающиеся `impl`) не вводится.
- **Наследования реализации в 1.0 нет.** Повторное использование кода:
  - методы трейтов по умолчанию — вместо базового класса с общей логикой;
  - делегирование `extend Тип: Трейт by self.поле` — во вложенный объект пересылаются только **обязательные** методы, не реализованные явно; методы по умолчанию вызываются на самом объекте и видят его переопределения (Р-8);
  - обобщения с ограничениями, расширения `extend`, `@derive`, композиция.
  Корпус примеров подтвердил, что для ниши 1.0 этого достаточно ([CORPUS_REVIEW.md](../CORPUS_REVIEW.md), раздел 5).
- **Реализации трейтов и расширения** записываются одной конструкцией: `extend Тип { … }` и `extend Тип: Трейт { … }` ([ADR-0010](0010-syntax.md)).
- **`class`** (после 1.0, ADR-0018) — ссылочный тип с подсчётом ссылок и идентичностью, сахар над `Shared`, без наследования реализации.
- **Extension functions** — статически разрешаемые методы; трейты они не реализуют. Порядок разрешения: собственные методы → методы трейтов в области видимости → расширения.
- **Перегрузка операторов** — через трейты. **Перегрузки функций по типам нет**; есть именованные аргументы и значения по умолчанию.
- Не вводятся: типы высших порядков (HKT), неявные преобразования.

## Причины выбора

- Одно понятие интерфейса вместо двух.
- Мономорфизация даёт предсказуемую производительность и проще реализуется поверх LLVM.
- Специализация реализаций в Rust годами остаётся нестабильной из-за проблем корректности.
- Без наследования нет вариантности классов, мостов методов, хрупкого базового класса.
- Без перегрузки по типам проверка типов остаётся быстрой и предсказуемой (опыт Swift показывает обратное).

## Последствия

- Разработчикам на Kotlin и Java нужно привыкнуть к композиции вместо наследования.
- Время компиляции и размер кода растут с числом экземпляров обобщений; нужны меры на этапе 4 (общий код для экземпляров с одинаковой раскладкой).
- Когерентность ограничит реализацию чужих трейтов для чужих типов.

## Риски

- **GUI-фреймворки** исторически опираются на наследование; привычные паттерны переносятся хуже. Снижение: UI — после 1.0; современные декларативные фреймворки (Compose, SwiftUI) обходятся композицией.
- **Раздувание кода** из-за мономорфизации. Снижение: измерения, общий код для одинаковых раскладок.

## Статус и условия пересмотра

Предварительно принято для этапа 0, включая отказ от наследования и перенос `class` за 1.0. Окончательно — в точке G0. Детали `class` — после 1.0, по опыту работы с `Shared` (Q-25).
