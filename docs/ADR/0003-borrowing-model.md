# ADR-0003. Модель заимствований

- **Статус:** предварительно принято для этапа 0 (05.11.2026); уточнение «условная невыходящесть» принято 05.11.2026 (Q-40); окончательно — в точке G1
- **Дата:** 2026-11-04 (версия 2 — 2026-11-05, после корпуса примеров)
- **Связано:** [ADR-0002](0002-memory-model.md), [ADR-0005](0005-concurrency.md), [ADR-0010](0010-syntax.md); [ARCHITECTURE_REVIEW.md](../ARCHITECTURE_REVIEW.md) §3.4, §5.2 (M2), §5.3; [CORPUS_REVIEW.md](../CORPUS_REVIEW.md); вопросы Q-05, Q-18, Q-19, Q-40; эксперименты E-1, E-6

## Проблема

Заимствования дают доступ к данным без копирования и без передачи владения. Модель Rust — первоклассные ссылки с параметрами времени жизни — выразительна и проверена, но именно она главный источник сложности для новичков: аннотации времени жизни в сигнатурах и структурах, вариантность, `Pin`, невозможность самоссылающихся структур. С ней цель «удобства Kotlin» недостижима.

**Условие инициатора (05.11.2026):** модель должна быть понятнее Rust, но без отказа от безопасности. В безопасном коде невозможны некорректный доступ к памяти, использование после освобождения и гонки данных.

## Возможные варианты

- **А.** Модель Rust: ссылки — типы `&'a T`, хранятся в структурах, у типов есть параметры времени жизни.
- **Б.** Ссылки второго класса: только параметры и локальные переменные; нельзя хранить в полях и возвращать (исследовательский язык Hylo).
- **В.** Вариант Б + возврат заимствований с выводимой зависимостью от параметра + невыходящие типы-представления. Это направление Swift (`borrowing`, невыходящие типы, `Span`) и C# (`ref struct`, `scoped`).
- **Г.** Заимствования с подсчётом во время выполнения. Так сделано в Inko: уничтожение владельца при живых заимствованиях — ошибка во время выполнения.
- **Д.** Без заимствований: копирование, перемещение и подсчёт ссылок.

## Рекомендуемое решение

Вариант **В**:

- **Заимствование — режим передачи параметра.** По умолчанию — неизменяемое заимствование; `inout` — исключительное изменяемое; `consume` — передача владения. Изменяемое заимствование отмечается на месте вызова (`&x`).
- **Возврат заимствования.** Источник выводится: у метода — `self`, у функции — единственный заимствованный параметр. В остальных случаях — аннотация `@borrows(a, b)` (Q-18). Заимствованный элемент обобщённого типа помечается в типе результата: `ref T` (чтение) или `inout T` (изменяемая проекция).
- **Локальное заимствование — явное:** `val e = ref list[i]`. Без `ref` попытка взять не-`Copy` элемент — ошибка с подсказкой.
- **Невыходящие значения** нельзя сохранить в выходящем месте: поле обычной структуры, `Shared`, глобальная переменная, выходящее замыкание. Все API, способные «потерять» значение без вызова деструктора (`forget`, `Shared`), принимают только выходящие типы.
- **Уточнение по итогам корпуса — условная невыходящесть** (Р-10, Q-40, принято 05.11.2026). Невыходящесть — структурное свойство типа, которое выводится, как `Send`. Тип, содержащий заимствование (список представлений, итератор с заимствующим замыканием, структура с полем `str`), сам становится невыходящим. Его можно держать в локальной переменной, передавать и возвращать с зависимостью от источника, но нельзя сохранить в выходящем месте.
- **Проверка** — внутрипроцедурный анализ потока данных на KIR в духе NLL, с двухфазными заимствованиями (`list.push(list.len())`).
- **Внутреннее представление** проверки использует переменные регионов: так можно будет добавить именованные времена жизни, если они понадобятся.

## Как модель обеспечивает гарантии

| Гарантия | Механизм |
|---|---|
| Нет использования после освобождения | Перемещённое значение недоступно; заимствование не переживает источник; невыходящее значение нельзя сохранить там, где оно переживёт источник |
| Нет некорректного доступа к памяти | Пока элемент заимствован, коллекцию нельзя изменить; проверка границ; `null` только у `T?`; сырые указатели разыменовываются только в `unsafe` |
| Нет гонок данных | Изменяемое заимствование исключительно; между потоками — только `Send`/`Sync` ([ADR-0005](0005-concurrency.md)) |

Как это видно в примерах — [CORPUS_REVIEW.md](../CORPUS_REVIEW.md), раздел 4.

## Причины выбора

- Корпус из 44 примеров: аннотация источника заимствования понадобилась один раз, аннотаций времени жизни в структурах нет.
- Нет вариантности по временам жизни, самоссылающихся структур и `Pin` в пользовательском API.
- Невыходящие кадры задач делают возможным безопасное заимствование в структурированной конкурентности ([ADR-0005](0005-concurrency.md)).
- Направление совпадает с эволюцией Swift и C#.

## Последствия

- Структуры, которые в Rust держат ссылки и при этом должны жить долго, в KENOX держат владеющие данные, индексы или `Shared`. Короткоживущие структуры с представлениями возможны как невыходящие (Р-10).
- Арены работают через дескрипторы `Id<T>` ([ADR-0002](0002-memory-model.md)).
- Пользователю проще; межпроцедурная часть проверки проще для компилятора; внутрипроцедурная остаётся сложной, а условная невыходящесть добавляет работы в проверку типов.
- Заимствование по умолчанию не меняет производительность: тривиальные типы ABI передаёт по значению.

## Риски

- **Модель проверена меньше, чем у Rust;** возможны дыры в корректности. Снижение: формальная модель на шаге 0.4 (в первую очередь — условная невыходящесть, результаты-заимствования, режимы привязок, захват в замыканиях), отрицательные тесты, независимое ревью.
- **Выразительности не хватит** для отдельных задач (например, статической привязки дескрипторов к арене). Снижение: точка решения G1; запасной путь — ограниченные именованные времена жизни.

## Статус и условия пересмотра

Основа модели предварительно принята для этапа 0; уточнения по итогам корпуса (условная невыходящесть, `ref T`, явный `ref`) приняты 05.11.2026. Формальная модель — шаг 0.4. Обязательный пересмотр — в точке G1 (после вехи 1e), на реальном компиляторе.
