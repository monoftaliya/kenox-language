# ADR-0013. Взаимодействие с C (FFI) и расширяемая архитектура привязок

- **Статус:** предлагается
- **Дата:** 2026-11-04
- **Связано:** [ADR-0006](0006-compiler-architecture.md), [ADR-0007](0007-errors-and-panics.md), [ADR-0026](0026-gc-readiness.md); [ARCHITECTURE.md](../ARCHITECTURE.md) §7; аудит §3.6; [CORPUS_REVIEW.md](../CORPUS_REVIEW.md) (Р-23, Р-24, Р-26); вопросы Q-15, Q-29, Q-37, Q-38, Q-41

## Проблема

Требования (ответ от 04.11.2026): программы на KENOX должны вызывать функции C-библиотек, предоставлять свои функции для вызова из C, работать с внешними библиотеками, использоваться как библиотеки внутри других программ и быть совместимыми с системной инфраструктурой. Более глубокая интеграция с C++, JVM/Kotlin и Swift — позже, но архитектура FFI должна допускать её без переделки.

Сложности:
- C ABI — ответственность фронтенда: правила раскладки аргументов по регистрам свои на каждой платформе (аудит §3.6).
- На границе с C гарантии безопасности KENOX заканчиваются.
- Библиотека KENOX внутри чужой программы не управляет ни потоками, ни порядком инициализации.

## Возможные варианты

- **А.** Ручные объявления `extern` + `@repr(C)` + внешние инструменты для заголовков (модель Rust: bindgen, cbindgen).
- **Б.** Импорт C-заголовков прямо в компиляторе через встроенный clang (`@cImport` в Zig, Clang importer в Swift).
- **В.** Отдельный язык описания интерфейсов (IDL) и генерация кода для обеих сторон (UniFFI, WIT в Component Model).
- **Г.** Слои: ручные объявления в языке (как в А) + машиночитаемое описание экспортированного API, которое выдаёт компилятор, + генераторы поверх этого описания (идея В без отдельного IDL).

## Рекомендуемое решение

Вариант **Г**.

**1. Язык**
- `extern "C"` — импорт функций и глобальных переменных; вызов всегда `unsafe`.
- `@export` + `extern "C"` — экспорт функции под стабильным C-именем, без искажения имён.
- `@repr(C)` — C-раскладка структур; перечисления с явным целым типом — для C-совместимых перечислений.
- Типы указателей на функции с ABI C — для обратных вызовов; пользовательские данные — через сырой указатель.
- `CStr` (заимствованная строка с нулём в конце) и `CString` (владеющая). Указатель, полученный из `CString`, — невыходящее представление, привязанное к строке: висячий указатель от временной `CString` становится ошибкой компиляции; для простых случаев — `withCString(s) { p -> … }` (уточнение по корпусу, Р-23).
- Значения перечислений, пришедшие из C, принимаются как целые (`CInt`) и проверяются (`tryFrom`): C может вернуть число вне списка вариантов (Р-24).
- Вызов C-функций с переменным числом аргументов (`printf`) — да; объявление таких функций на KENOX — нет.
- Автотрейт «C-совместимость»: компилятор отвергает в сигнатурах `extern` и `@export` типы без определённой C-раскладки.
- Паника, дошедшая до границы `@export`, — аварийное завершение процесса: раскрутка через C-кадры — неопределённое поведение.
- Передача владения через границу — явными функциями (`intoRaw`/`fromRaw`). Память, выделенную KENOX, освобождает KENOX — для этого библиотека экспортирует функции освобождения.

**2. Сборка**
- `kenox.toml` объявляет тип артефакта: `bin`, `staticlib`, `dylib`.
- Предложение по корпусу (Р-26, этап 3, Q-41): секция `[native]` собирает C-исходники пакета тем же clang, что и сам KENOX.
- Подключение нативных библиотек: имя, тип связывания, пути поиска; позже — pkg-config.

**3. Инструменты**
- Генератор C-заголовка по экспортированным функциям и типам — в 1.0.
- Импорт C-заголовков — отдельный инструмент на libclang, а не часть компилятора; в 1.0, если успеет, иначе 1.x (Q-37).

**4. Описание API — точка расширения**
- Компилятор выдаёт машиночитаемое описание экспортированного API в версионируемом формате (Q-38): типы, функции, владение, nullable, кто освобождает память.
- Генератор C-заголовка — первый потребитель описания. Генераторы для Kotlin/JNI, Swift, C++, Python — после 1.0, поверх того же описания.

**5. Правила вызова**
- Отдельный крейт `kenox_abi`: перечисление соглашений о вызове (`C`, позже другие) и таблицы для каждой платформы. Им пользуются кодогенерация и инструменты.

**6. Библиотека внутри чужой программы**
- Нет глобальных конструкторов с побочными эффектами: статические значения вычисляются при компиляции или лениво.
- Runtime лениво инициализирует состояние потока при первом вызове из чужого потока.
- Глобальные переменные в безопасном коде — только `Sync` или под `Mutex`, поэтому экспортированные функции потокобезопасны по отношению к глобальному состоянию по построению.

**7. Стабильность**
- Стабильна только граница C. Стабильный ABI между версиями KENOX не обещается (Q-29).

## Причины выбора

- Ручные объявления + `@repr(C)` — проверенная модель; не требует встраивать clang в компилятор.
- Описание API отделяет генераторы от компилятора: новый язык — новый генератор, без изменений компилятора. Похожим путём идут инструменты генерации привязок вроде UniFFI.
- Без глобальных конструкторов и с ленивой инициализацией потоков библиотеку можно встраивать в чужую программу.

## Последствия

- Пока нет импортёра заголовков, объявления C-функций пишутся вручную или генерируются внешним инструментом.
- `kenox_abi` — критичный компонент: нужны тесты совместимости вызовов с кодом, собранным clang, на каждой платформе.
- Формат описания API становится публичным контрактом — его нужно версионировать.

## Риски

- **Тонкие ошибки ABI:** структуры по значению, выравнивание, `bool`, `long` (на Windows — 32 бита, на Linux и macOS — 64). Снижение: автоматически генерируемые тесты «KENOX вызывает C» и «C вызывает KENOX» на сотнях сигнатур.
- **Обратные вызовы из чужих потоков.** Снижение: данные, передаваемые в обратный вызов, должны быть `Send`, где это можно проверить; остальное — документация.
- **Описание API не подойдёт будущим языкам** (исключения, наследование). Снижение: формат версионируется; первые потребители — C, затем Kotlin/JNI.

## Статус и условия пересмотра

Предлагается. Синтаксис атрибутов — вместе с ADR-0010. Формат описания API — до этапа 3.
