# ADR-0025. Спецификация языка: формат и нормативность

- **Статус:** предлагается — утверждается вместе с главой 1 спецификации
- **Дата:** 2026-11-05
- **Связано:** [ADR-0010](0010-syntax.md), [ADR-0027](0027-ai-assisted-development.md); [ROADMAP.md](../ROADMAP.md), шаги 0.3–0.5; [spec/README.md](../../spec/README.md)

## Проблема

На шаге 0.3 появляется спецификация ядра. Код компилятора будет писать ИИ, а инициатор не читает его построчно ([ADR-0027](0027-ai-assisted-development.md)). Значит, нужен точный документ, с которым сверяются компилятор и тесты, и способ проверять, что документ, тесты и примеры не расходятся.

## Возможные варианты

- **А.** Справочник в прозе без формальных элементов.
- **Б.** Полная формальная семантика (K Framework, Coq, Lean).
- **В.** «Спецификация — это реализация»: поведение компилятора и есть определение языка.
- **Г.** Проза с нумерованными правилами, грамматика в EBNF, примеры ✓/✗, машинные проверки согласованности; формальная модель — только для заимствований (шаг 0.4).

## Рекомендуемое решение

Вариант **Г**:

- Спецификация лежит в `spec/`, по главе на файл, на русском языке, как остальная документация.
- Нормативное правило — абзац с идентификатором вида `[lex.ident.syntax]`; префикс обозначает главу. Идентификатор стабилен: на него ссылаются тесты, диагностика и другие правила. Всё остальное — пояснения.
- Грамматика — EBNF в блоках `ebnf`; лексические правила — ЗАГЛАВНЫМИ, синтаксические — СловамиСЗаглавной.
- Примеры: ✓ — допустимый код, ✗ — закомментированный код с идентификатором нарушенного правила. На шаге 0.5 примеры становятся тестами.
- `cargo test` проверяет: идентификаторы правил уникальны, ссылки на правила существуют, каждое правило грамматики определено один раз и используется, примеры ✓ написаны по эскизу.
- Формальная модель строится только для заимствований — там, где ошибка стоит дороже всего (шаг 0.4).
- Изменения спецификации в версиях 0.x — через pull request вместе с примерами и тестами. Гарантии стабильности — с версии 1.0 (этап 5).

## Причины выбора

- Нумерованные правила связывают спецификацию с тестами: у каждого отрицательного теста есть правило, которое он проверяет. Похожий подход используют Ferrocene Language Specification и Rust Reference — у их правил тоже есть стабильные идентификаторы.
- Полная формальная семантика (Б) — работа на годы и требует специалиста; для ниши 1.0 она не окупается, кроме модели заимствований.
- Вариант В не даёт ничего, с чем можно сверить код, написанный ИИ.

## Последствия

- Каждая новая возможность сначала описывается правилами, затем покрывается тестами, затем реализуется ([ADR-0027](0027-ai-assisted-development.md), порядок внутри инкремента).
- Спецификация растёт по главам; главы о смысле программ описывают только ядро 0.1.

## Риски

- **Спецификация отстанет от компилятора.** Снижение: правило «возможность готова, только когда описана и покрыта тестами»; машинные проверки ссылок между тестами и правилами.
- **Спецификация только на русском** затруднит внешних участников. Снижение: перевод — после стабилизации ядра; идентификаторы правил и грамматика не зависят от языка текста.

## Статус и условия пересмотра

Предлагается; утверждается вместе с главой 1. Пересмотр — в точке G0, по опыту написания глав 1–7.
