# ADR-0006. Архитектура компилятора, IR и backend

- **Статус:** предлагается
- **Дата:** 2026-11-04 (версия 2: backend v0 и эталонный интерпретатор с первой вехи)
- **Связано:** [ADR-0008](0008-compile-time-and-metaprogramming.md), [ADR-0013](0013-ffi.md), [ADR-0026](0026-gc-readiness.md), [ADR-0027](0027-ai-assisted-development.md); [ARCHITECTURE.md](../ARCHITECTURE.md) §9; аудит §2.4, §3.5, §3.6, §3.10, §4; вопросы Q-15, Q-28; эксперименты E-4, E-8

## Проблема

Нужно выбрать язык реализации, конвейер, промежуточные представления, backend и стратегию поддержки IDE так, чтобы MVP был достижим, а развитие не потребовало переписывания компилятора.

После ответа от 04.11.2026 добавились требования: компилятор разрабатывает один человек с помощью ИИ ([ADR-0027](0027-ai-assisted-development.md)). Значит, сборка должна быть максимально простой, а корректность сгенерированного кода — проверяемой автоматически.

## Возможные варианты

- **Язык реализации:** Rust; C++ (прямой доступ к API LLVM); OCaml; Kotlin/JVM; Zig; самохостинг с самого начала.
- **IR:** только AST → LLVM IR; AST → собственный средний IR → LLVM IR; диалект MLIR.
- **Backend:** текстовый LLVM IR + внешний clang; LLVM как библиотека; C как промежуточный язык; Cranelift; собственный.
- **Фронтенд:** пакетный конвейер или фронтенд, ориентированный на запросы (инкрементальный).

## Рекомендуемое решение

- **Язык реализации — Rust.** Самохостинг — не раньше 1.0, возможно никогда (Q-28).
- **Конвейер:** Lexer → Parser (CST без потерь, устойчивый к ошибкам) → AST → разрешение имён → HIR (рассахаривание) → проверка типов и трейтов → KIR (граф управления) → проверка перемещений и заимствований → расстановка деструкторов, мономорфизация → кодогенерация.
- **KIR** — собственный средний IR. На нём все семантические проверки, а позже — оптимизации уровня языка. Виды указателей сохраняются до кодогенерации ([ADR-0026](0026-gc-readiness.md)).
- **Эталонный интерпретатор KIR — с вехи 1a.** Каждая тестовая программа выполняется интерпретатором и в машинном коде; результаты сравниваются. Позже интерпретатор вычисляет `const fun` и проверяет неопределённое поведение в `unsafe`-коде.
- **Backend v0 (MVP и, возможно, до 1.0) — текстовый LLVM IR + clang.** Компилятор пишет `.ll`, clang оптимизирует, компилирует и линкует (стартовый код, системные библиотеки). LTO включается флагами clang. Поддерживаемый диапазон версий clang фиксируется (ориентир — 18 и новее) и проверяется в CI (E-8).
- **Backend v1 (до 1.0, только если понадобится) — LLVM как библиотека** через C API с закреплённой версией. Поводы перейти: скорость компиляции, управление проходами оптимизации, поставка единым дистрибутивом.
- **Граница KIR → backend оформлена как интерфейс.** Быстрый backend для Debug (кандидат — Cranelift) — после 1.0.
- **Фронтенд, ориентированный на запросы:** стабильные идентификаторы, интернирование, чистые функции, без глобального изменяемого состояния. Библиотека инкрементальности — после 1.0.
- **`kenox_abi`** — отдельный крейт с правилами вызова C для x86-64 System V, Win64, AArch64 (включая вариант Apple), позже wasm32. Следить за библиотекой ABI в LLVM: в 2025 году её прототип покрывал только x86-64 Linux и BPF.
- **Текстовые дампы каждого IR** (`--dump=ast|hir|kir|llvm`) в стабильном формате.
- **Runtime и std** пишутся на KENOX.

## Причины выбора

- **Rust:** алгебраические типы и `match` удобны для компиляторов; производительность; экосистема (лексеры, парсеры, диагностика, Cranelift, привязки к LLVM). Прецедент — Inko: компилятор на Rust с LLVM; авторы отказались от самохостинга ради простоты.
- **Средний IR:** LLVM IR не знает о владении, трейтах и async. Rust (MIR), Swift (SIL) и Inko (MIR) пришли к этому решению.
- **Текстовый IR + clang:** компилятор собирается `cargo build` без библиотек LLVM — это критично для работы одного человека с ИИ. Вывод читаем. Clang берёт на себя линковку и стартовый код на всех платформах. Официальная политика LLVM: текстовый формат IR не обещает обратной совместимости, хотя меняется редко; биткод совместим, но для его генерации нужны библиотеки LLVM [факт]. Риск управляем через диапазон версий и CI.
- **Интерпретатор с первой вехи:** автоматический оракул для кода, написанного ИИ; тот же компонент потом даёт CTFE и проверку UB.
- **Ориентация на запросы:** без неё IDE потребует отдельного фронтенда, как случилось с rust-analyzer.

## Последствия

- Для сборки программ на KENOX нужен установленный clang (на Windows — ещё библиотеки MSVC или MinGW, Q-15). Позже тулчейн может поставлять clang и lld в комплекте.
- Каждая сборка запускает отдельный процесс и разбирает текст — для MVP приемлемо; время измеряется (E-4).
- Пока нет быстрого backend, отладочные сборки на LLVM медленнее, чем могли бы быть. Для сравнения: Zig в 0.15 сделал собственный x86_64-backend стандартным для Debug и ускорил отладочную компиляцию примерно в пять раз, но код получается медленнее, чем у LLVM без оптимизаций.
- Дисциплина: логика языка — только в KIR, не в кодогенерации.

## Риски

- **Изменения текстового IR между версиями clang** ломают сборку. Снижение: диапазон версий, CI с минимальной и последней версией (E-8), минимальное подмножество IR; при необходимости — переход на backend v1.
- **Обновления LLVM** выявляют ошибки оптимизатора. Снижение: обновление — отдельная задача с полным прогоном тестов.
- **Архитектура на запросах сложнее** для первой реализации. Снижение: соблюдать принципы (идентификаторы, чистые функции), не подключая библиотеку инкрементальности.
- **Своя реализация C ABI** — источник тонких ошибок. Снижение: тесты совместимости вызовов с кодом, собранным clang, на каждой платформе.

## Статус и условия пересмотра

Предлагается; язык реализации подтверждает исходный выбор. Переход на backend v1 — по данным E-4 и E-8. Пересмотр отладочного backend — если время сборки станет главной жалобой.
