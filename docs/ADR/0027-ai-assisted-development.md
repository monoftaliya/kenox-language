# ADR-0027. Разработка одним человеком с помощью ИИ: процесс и ограничения архитектуры

- **Статус:** предлагается
- **Дата:** 2026-11-04 (версия 2 — 2026-11-05: Windows 11, GitHub, рабочий цикл)
- **Связано:** [ADR-0006](0006-compiler-architecture.md); [ARCHITECTURE.md](../ARCHITECTURE.md) §9, §10; [ROADMAP.md](../ROADMAP.md); вопросы Q-15, Q-17, Q-35

## Проблема

Ответ от 04.11.2026: команды и бюджета нет. Инициатор задаёт концепцию, требования и решения, запускает и тестирует результат, даёт обратную связь. Основную работу по проектированию и коду выполняет Claude; ChatGPT используется для независимого анализа. Жёсткого срока нет, качество важнее скорости.

Риски такого режима:
- **Потеря контекста между сессиями.** Каждая сессия начинается с неполной картины; решения, не записанные в репозитории, теряются или искажаются.
- **Правдоподобный, но неверный код.** В компиляторе это особенно опасно: ошибка в проверке заимствований или кодогенерации даёт программы, которые тихо работают неправильно.
- **Соблазн объёма.** ИИ быстро пишет код — легко добавить лишнее и потом его поддерживать.
- **Ограниченное ревью.** Инициатор не обязан читать внутренности компилятора, значит, качество должно подтверждаться автоматически.
- **Разные окружения.** Облачное окружение Claude — Linux, основная среда инициатора — Windows 11 (ответ от 05.11.2026). Окончания строк, пути и набор инструментов различаются.
- **Трение при сборке.** Если для сборки компилятора нужно ставить библиотеки LLVM, каждый запуск превращается в проблему.

## Возможные варианты

- **А.** Свободная работа по сессиям: «сделай следующую функцию».
- **Б.** Структурированный процесс: репозиторий как единственный источник истины, спецификация и тесты до кода, малые проверяемые инкременты, автоматическая проверка, независимое ревью по протоколу.
- **В.** Вариант Б + ограничения архитектуры, облегчающие такую работу.

## Рекомендуемое решение

Вариант **В**.

**Процесс**
1. **Репозиторий — единственный источник истины:** ARCHITECTURE.md, ADR, спецификация (`spec/`), ROADMAP.md, OPEN_QUESTIONS.md, а также два служебных файла:
   - `CLAUDE.md` — правила для сессий ИИ: как собирать и тестировать, инварианты, запреты;
   - `STATUS.md` — где мы сейчас: текущая веха, что сделано, что дальше, известные проблемы. Обновляется в конце каждой сессии.
2. **Инкремент — единица работы:** одна цель из ROADMAP; примерно 300–800 строк вместе с тестами; всё собирается и все тесты проходят; запись в STATUS.md; коммит. Инициатор проверяет результат запуском команды и примера, а не чтением кода.
3. **Порядок внутри инкремента:** спецификация (если меняется семантика) → тесты → реализация.
4. **Новая возможность — только через ROADMAP или ADR.** Решения, меняющие язык, утверждает инициатор.
5. **Независимое ревью по протоколу.** ChatGPT получает спецификацию, ADR и изменения. Задача — найти контрпример: программу, которую компилятор должен отвергнуть, но принимает (или наоборот), и непокрытые случаи. Каждая находка становится тестом. Поиск контрпримеров — самое ценное применение второй модели.
6. **CI на трёх ОС** (GitHub Actions; для публичных репозиториев стандартные раннеры бесплатны). Вручную проверять каждую ОС не нужно.

**Репозиторий и рабочий цикл** (ответ от 05.11.2026: публичный репозиторий `kenox-language` на GitHub, CI на Windows, Linux и macOS; инструкции должны быть согласованными и понятными). Реализовано на шаге 0.1; порядок действий — [WORKFLOW.md](../WORKFLOW.md).
1. **Ветка `main` всегда зелёная.** Каждый инкремент — отдельная ветка и pull request. CI проверяет его на трёх ОС; в `main` попадает только pull request с зелёным CI.
2. **Описание pull request — по шаблону:** цель, что изменилось, как проверить (одна-две команды), что не сделано. Это материал для вашей приёмки и для ревью ChatGPT.
3. **Приёмка — слияние.** Вы смотрите статус CI и описание; при желании запускаете проверку у себя. Слияние pull request выполняете вы, способом Squash and merge: один инкремент — один коммит в `main`. Слияние и есть утверждение инкремента.
4. **Одна команда проверки для всех — `cargo test`:** локально в PowerShell, в bash и в CI запускается одно и то же. Проверки документов, корпуса и C-кода примеров — тесты инструмента `tools/repo-check` на Rust без внешних зависимостей. Поэтому результат на вашей машине и в CI не расходится, а для проверок не нужен ни Python, ни bash. CI дополнительно проверяет оформление кода на Rust (`cargo fmt`, `cargo clippy`) — это забота Claude.
5. **Одна инструкция — `docs/WORKFLOW.md`:** установка инструментов на Windows 11, клонирование, команда проверки, работа с pull request. `CLAUDE.md`, `README.md` и шаблон pull request ссылаются на неё, а не пересказывают.

**Ограничения архитектуры**
1. Компилятор собирается `cargo build` без внешних библиотек; для запуска нужен только clang (backend v0, [ADR-0006](0006-compiler-architecture.md)).
2. Небольшие крейты с документированными интерфейсами — такие, чтобы крейт целиком помещался в контекст одной сессии.
3. Никакого глобального изменяемого состояния; сущности адресуются индексами; вывод детерминирован.
4. Текстовые дампы каждого IR в стабильном формате — для отладки и snapshot-тестов.
5. Эталонный интерпретатор KIR с первой вехи — автоматический оракул для кодогенерации.
6. Минимум внешних зависимостей, закреплённые версии: Rust — в `rust-toolchain.toml`, зависимости — в `Cargo.lock` (`--locked` в CI). Новая внешняя зависимость — только через ADR.
7. Тесты — около половины объёма работы: положительные и отрицательные (запрещённые программы) на каждое правило спецификации; snapshot-тесты диагностики; дифференциальные тесты (интерпретатор против машинного кода); fuzzing — с вехи владения.
8. Вывод компилятора и инструментов не зависит от ОС: в репозитории окончания строк LF (`.gitattributes`), пути в диагностике и дампах — относительные, с `/`. Иначе одни и те же snapshot-тесты на Windows и Linux расходятся.

## Причины выбора

- В компиляторе правдоподобный код часто оказывается ошибочным. Автоматическая проверка — единственный масштабируемый способ доверять коду, который инициатор не читает.
- Записанные решения не теряются между сессиями.
- Малые инкременты дают раннюю обратную связь и дешёвые откаты.

## Последствия

- Код пишется медленнее, чем в «свободном» режиме: тесты и документы занимают заметную часть работы.
- Инициатор — владелец решений и приёмки, а не ревьюер кода.
- Первая платформа разработки — Linux x86_64 (окружение Claude), вторая — Windows x86_64 с MSVC (основная среда инициатора, Q-15). macOS проверяется в CI с первого шага.

## Риски

- **Узкое место — время инициатора** на проверку и решения. Снижение: решения пакетами, чёткие критерии приёмки, автоматические отчёты CI.
- **Спецификация и код расходятся.** Снижение: правило «возможность готова, только когда она описана и покрыта тестами»; сверка при ревью.
- **Трудные ошибки,** на которых ИИ ходит по кругу (решатель трейтов, заимствования). Снижение: минимальные воспроизводящие примеры, независимое ревью, при необходимости — упрощение дизайна.

## Статус и условия пересмотра

Предлагается. Рабочий цикл с GitHub реализован на шаге 0.1 ([WORKFLOW.md](../WORKFLOW.md)) и окончательно утверждается вашим первым слиянием pull request. Пересмотр — после вехи 1b: сработал ли процесс на первых инкрементах.
