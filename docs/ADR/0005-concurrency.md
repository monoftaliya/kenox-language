# ADR-0005. Конкурентность и асинхронность

- **Статус:** принято 2026-11-05: в 1.0 — синхронное выполнение и потоки, async/await — в 1.1; async-runtime на первых этапах не создаётся
- **Дата:** 2026-11-04 (версия 3 — 2026-11-05: что закладывается в 1.0 ради async)
- **Связано:** [ADR-0002](0002-memory-model.md), [ADR-0003](0003-borrowing-model.md), [ADR-0026](0026-gc-readiness.md); [ARCHITECTURE.md](../ARCHITECTURE.md) §5, §6; аудит §2.3, §3.3, §3.4, §3.5; вопросы Q-12, Q-23, Q-24, Q-34; эксперимент E-6

## Проблема

Исходно предложены async/await, структурированная конкурентность, лёгкие задачи, каналы, акторы, мьютексы и атомики, отмена, пул потоков, work stealing и параллельное выполнение — без разделения на язык и библиотеку и без увязки с владением.

Ключевые конфликты async (аудит §3.4): заимствование через `await`, отмена при I/O с заимствованными буферами, заимствование данных родителя в дочерних задачах, раскол экосистемы между runtime, браузер без блокировок главного потока.

После ответа от 04.11.2026 добавился вопрос объёма. Ниша 1.0 — инструменты, серверы, утилиты, библиотеки и вычисления на CPU, а правило объёма требует «три хорошие возможности вместо десяти». Нужно решить, что из конкурентности входит в 1.0.

## Возможные варианты

**Модель:**
1. **Stackful** — зелёные или виртуальные потоки (Go, Java Loom). Нет окраски функций, но runtime должен управлять стеками; это несовместимо с дешёвым вызовом C, а в Wasm нет общего stack switching.
2. **Stackless, future как значения, отмена уничтожением future** (Rust). Минимальный runtime, но `Pin`, «безопасность к отмене», невозможность безопасных заимствованных буферов при I/O с завершением, раскол runtime.
3. **Stackless без future как пользовательских значений:** структурированная конкурентность как конструкция языка, задачи доходят до конца, кооперативная отмена (Swift, Kotlin).
4. **Акторы как основа** (Pony, Erlang, акторы Swift).

**Объём 1.0:**
- **А.** Потоки, синхронизация, каналы, пул, параллельные итераторы **и** async/await.
- **Б.** Потоки, синхронизация, каналы, пул, параллельные итераторы; async/await — в 1.1.
- **В.** Только потоки и синхронизация; остальное — библиотеки сообщества.

## Рекомендуемое решение

Модель — **3**, объём 1.0 — **Б**.

**В 1.0:**
- Свобода от гонок — автотрейты `Send`/`Sync`; модель памяти атомиков — C++20/LLVM.
- Потоки ОС и структурированные потоки: дочерние потоки заимствуют данные родителя, а область потоков — конструкция, которую нельзя «потерять» (приём `thread::scope` из Rust).
- `Mutex`, `RwLock`, условные переменные, атомики, каналы — в std.
- Пул потоков и параллельные итераторы по срезам — для вычислений.
- Серверы — на пуле потоков и блокирующем I/O.

**В 1.1 — async/await по модели 3:**
- `async fun` компилируется в конечный автомат на уровне KIR; вызов требует явного `await`.
- Future не являются пользовательскими значениями. Конкурентность — через области задач (привязки в духе `async let`, группы задач) и явные отдельные задачи; отдельная задача требует владения захваченными данными и `Send`.
- Задача освобождается только после завершения; отмена кооперативная, доставляется в точках `await`; при выходе из области дочерние задачи отменяются, и область дожидается их завершения.
- Дочерние задачи в области могут заимствовать данные родителя (корректность — эксперимент E-6).
- Кадры задач не перемещаются после создания: `Pin` в пользовательском API нет.
- Интерфейсы исполнителя и I/O, а также исполнитель по умолчанию — в std: однопоточный для браузера, встраиваемых систем и UI, многопоточный с work stealing для серверов.
- Акторы — библиотека поверх задач и каналов.

**Что закладывается в 1.0, чтобы async добавился в 1.1 без переработки** (требование инициатора от 05.11.2026). Async-runtime при этом не создаётся.

| Часть | Что делается в 1.0 | Почему этого достаточно |
|---|---|---|
| Компилятор | Анализ «что живо в какой точке» на KIR — он нужен и для проверки заимствований. Трансформации KIR оформлены как независимые проходы | async — ещё один проход KIR → KIR (кадр → конечный автомат). Фронтенду понадобятся только синтаксис и типизация `async fun` |
| Система типов | Автотрейты `Send`/`Sync`; невыходящие типы ([ADR-0003](0003-borrowing-model.md)); ключевые слова `async` и `await` зарезервированы | Безопасность кадров задач выражается теми же автотрейтами и той же невыходящестью; новой системы не нужно |
| Модель памяти | Утечка допустима только для выходящих значений; невыходящее значение нельзя «потерять» | Это основание для безопасного заимствования данных родителя в дочерних задачах (E-6) |
| std | Блокирующие API названы и устроены так, чтобы рядом появились асинхронные; std не опирается на неизменность потока между двумя вызовами | Асинхронный I/O добавляется рядом, не ломая существующий код |
| Runtime | Потоки создаются через runtime std — точка регистрации есть ([ADR-0026](0026-gc-readiness.md)) | Исполнителю 1.1 понадобится та же точка |

Проверка: в точке G2 (конец этапа 2) — ревью, что ни одно решение этапов 1–2 не нарушает эти ограничения.

## Причины выбора

- Потоки, структурированные потоки, каналы и пул закрывают нишу 1.0: CLI, утилиты, библиотеки, вычисления, серверы умеренной нагрузки.
- async — самая рискованная возможность: корректность заимствований в задачах пока гипотеза (E-6). Перенос в 1.1 даёт время на формальную модель и не задерживает 1.0.
- Модель 3 сохраняет все преимущества: минимальный runtime, работа в Wasm без stack switching, безопасная отмена, заимствованные буферы при I/O с завершением, совпадение с асинхронной моделью WASI 0.3.

## Последствия

- Серверы на десятки тысяч одновременных соединений — после 1.1 (или раньше — через C-библиотеки событийного цикла по FFI).
- В 1.0 нет окраски функций; она появится в 1.1 вместе с async.
- После 1.1 синхронные и асинхронные API ввода-вывода будут сосуществовать — std должна это предусмотреть с самого начала.

## Риски

- **Пользователи серверной ниши сочтут 1.0 неполным без async.** Снижение: явная коммуникация; документированный путь «пул потоков + блокирующий I/O»; async — первая крупная возможность после 1.0.
- **Корректность заимствования в дочерних async-задачах** (E-6). Снижение: формальная модель до начала работ над 1.1; запасной путь — только перемещение данных в задачи.
- **Кооперативная отмена не прерывает долгие вычисления.** Снижение: явные проверки отмены, документация.

## Статус и условия пересмотра

Принято. Модель async — направление; детали — отдельным ADR-0019 до начала работ над 1.1.
