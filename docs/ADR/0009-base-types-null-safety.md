# ADR-0009. Базовые типы, null safety и арифметика

- **Статус:** предлагается
- **Дата:** 2026-11-04 (версия 2 — 2026-11-05, после корпуса примеров)
- **Связано:** [ADR-0004](0004-types-and-polymorphism.md), [ADR-0010](0010-syntax.md); [ARCHITECTURE_REVIEW.md](../ARCHITECTURE_REVIEW.md) §2.1, §2.5; [CORPUS_REVIEW.md](../CORPUS_REVIEW.md) (Р-4, Р-5, Р-25); вопросы Q-10, Q-11; эксперимент E-3

## Проблема

Для MVP нужны точные решения: набор примитивов, представление отсутствующего значения, семантика переполнения, строки и символы.

## Возможные варианты

- **Null:** `T?` как объединение, где `T??` = `T?` (Kotlin); `Option<T>` (Rust); `T?` как сахар над `Option<T>` (Swift).
- **Переполнение:** заворачивание (C, Java, Go); ловушка всегда (Swift); ловушка в отладке и заворачивание в релизе (Rust); ловушка всегда + явные операции.
- **Строки:** UTF-8 или UTF-16.
- **Целое размера указателя:** отдельные `ISize`/`USize` или `Int` размера указателя (Swift).

## Рекомендуемое решение

- **`T?` — синтаксический сахар для `Option<T>`.** Вложенные `Option<Option<T>>` различимы — это корректно для обобщённого кода. Литерал отсутствующего значения — `null`; есть `?.`, `?:` и явное извлечение с паникой. Умных приведений (smart cast) в 0.x нет: вместо них `if val` и `is` с привязками ([ADR-0010](0010-syntax.md)). Значения `null` вне `T?` не существует; nullable-указатели C представлены сырыми указателями с явной проверкой.
- **Ниши в раскладке:** `Option` от ссылки, `Box` или `Shared` не занимает лишней памяти.
- **Примитивы:** `Int8`–`Int64`, `UInt8`–`UInt64`, `Int` (= `Int64`), `ISize`, `USize`, `Float32`, `Float64`, `Bool`, `Char` (скалярное значение Unicode), `Unit`, `Never`. `Int128` — позже.
- **Переполнение — ловушка во всех профилях.** Явные операции заворачивания, насыщения и проверки (`wrappingAdd`, `saturatingAdd`, `checkedAdd`).
- **Строки:** `String` — владеющая UTF-8; `str` — заимствованное представление. Строковый литерал имеет тип `String` со статическим представлением, без выделения памяти, поэтому его можно хранить в полях и коллекциях (Р-4). Индексация — по байтовым смещениям; срез посреди символа — паника (Р-5); итерация — по `Char`; графемы — в библиотеке.
- **Длины и индексы — `Int`** (знаковый, 64 бита), как и обычная арифметика; `USize` — только на границе с C (Р-25, рекомендация Q-11). В корпусе преобразование понадобилось один раз.

## Причины выбора

- Сахар над `Option` даёт удобство Kotlin и однородность алгебраических типов Rust.
- Один целый тип для длин, индексов и арифметики убирает преобразования, которые в Rust загромождают индексный код (`as usize`); знаковость позволяет писать `i - 1` без ловушки на нуле. Цена — на 32-битных платформах (например, wasm32 после 1.0) длина коллекции хранится шире указателя; все платформы Tier 1 у 1.0 — 64-битные.
- Одинаковая семантика переполнения во всех профилях исключает класс ошибок «в отладке работает, в релизе ломается».
- UTF-8 — стандарт для ОС, сети, Wasm и C-библиотек.

## Последствия

- Проверка переполнения стоит производительности в горячих циклах — нужны явные операции и измерения (E-3).
- `s[i]` не возвращает символ за O(1). Это нужно объяснить разработчикам, пришедшим из Kotlin.

## Риски

- **Измеренная стоимость проверок переполнения окажется неприемлемой.** Снижение: измерение на этапе 1; при необходимости — пересмотр для профиля Performance с явной документацией (Q-10).

## Статус и условия пересмотра

Предлагается. Пересмотр семантики переполнения — по результатам E-3.
