# ADR-0001. Принципы дизайна, приоритеты и ниша 1.0

- **Статус:** принято 2026-11-04 (ниша и не-цели — по ответу инициатора); порядок приоритетов — предлагается
- **Дата:** 2026-11-04 (версия 2)
- **Связано:** все остальные ADR; [ARCHITECTURE.md](../ARCHITECTURE.md) §2, §3; аудит §0, §7.4; вопросы Q-01, Q-02, Q-34

## Проблема

Цели KENOX тянут в разные стороны: «быстро написать приложение» против «полного контроля для системного разработчика», семь доменов применения, гибкость против простоты. Без явного порядка приоритетов каждый спор будет решаться заново. Например: неявное копирование разделяемых ссылок удобнее, но скрывает стоимость. Язык начнёт расползаться.

Кроме того, нужен ответ на вопрос, для кого первая версия. Язык «для всех» на старте конкурирует со всеми сразу и не выигрывает ни у кого.

## Возможные варианты

1. Без явных приоритетов — решать каждый случай отдельно.
2. Приоритет производительности (C++, отчасти Rust).
3. Приоритет удобства (Kotlin, Go).
4. Явный упорядоченный список принципов + ниша 1.0 + список не-целей + правило объёма.

## Рекомендуемое решение

Вариант 4.

**Приоритеты при конфликте** (верхний побеждает нижний):

1. **Корректность безопасного подмножества.** Безопасный код не может вызвать неопределённое поведение или гонку данных. Это не обменивается ни на удобство, ни на скорость.
2. **Простая и единая модель.** Один способ управлять памятью (владение), один основной вид полиморфизма (трейты). Сложность раскрывается по мере необходимости.
3. **Предсказуемая производительность.** Никаких скрытых глобальных механизмов (пауз GC, неявных потоков). Стоимость конструкции либо видна в коде, либо задокументирована.
4. **Удобство чтения и написания кода.**
5. **Скорость компиляции и отзывчивость инструментов.** Последняя в порядке приоритетов, но с бюджетом, который измеряется в CI: регрессия скорости компиляции считается ошибкой.

**Правило объёма:** возможность попадает в 1.0, только если она нужна нише 1.0 и может быть доведена до качества релиза. Три хорошо реализованные возможности лучше десяти нестабильных.

**Ниша 1.0** (принято по ответу от 04.11.2026):
- инструменты разработчика и CLI-программы;
- серверные приложения;
- системные утилиты;
- библиотеки, в том числе встраиваемые в другие программы через C ABI;
- вычисления на CPU: SIMD и параллелизм на потоках.

**После 1.0:** приложения с графическим интерфейсом (архитектурный задел — ARCHITECTURE.md §8), WebAssembly, мобильные платформы, вычисления на GPU.

**Не-цели 1.0:**
- трассирующий GC (путь к нему сохранён — [ADR-0026](0026-gc-readiness.md));
- совместимость с JVM, Swift и C++ на уровне языка: интеграция идёт через C ABI, генераторы привязок — после 1.0 ([ADR-0013](0013-ffi.md));
- наследование реализации; макросы;
- стабильный ABI между версиями KENOX (стабильна только граница C);
- GUI-фреймворк в стандартной библиотеке; iOS;
- async/await — в 1.1 ([ADR-0005](0005-concurrency.md), принято 05.11.2026, Q-34).

## Причины выбора

- Явные ценности языка ускоряют решения и делают их предсказуемыми.
- Инструменты, утилиты, серверы и библиотеки требуют меньше всего платформенной работы (нет UI) и при этом нагружают всё ядро: память, конкурентность, I/O, производительность.
- Вычисления на CPU опираются на то же ядро (потоки, SIMD, контроль раскладки) и не требуют новых платформ.
- Библиотеки с C ABI — путь в существующие приложения без собственного UI-стека.

## Последствия

- Каждое следующее ADR ссылается на эти приоритеты и на правило объёма.
- Предложения, противоречащие не-целям, отклоняются без долгого обсуждения — до пересмотра этого ADR.
- Удобство уступает корректности: некоторые конструкции «как в Kotlin» станут явнее.

## Риски

- **Неверная ниша:** язык решает задачи, которых у целевых пользователей нет. Снижение — найти двух-трёх ранних пользователей с конкретной задачей до этапа 3.
- **Слишком строгий порядок приоритетов** для быстрого прототипирования. Снижение — пересмотр по итогам этапа 2.

## Статус и условия пересмотра

Ниша и не-цели приняты. Порядок приоритетов предлагается; если возражений не будет, он считается принятым по итогам этапа 0. Пересмотр — по итогам этапа 2 или при смене целевой аудитории.
