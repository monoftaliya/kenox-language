# ADR-0026. Готовность к будущему GC

- **Статус:** предлагается
- **Дата:** 2026-11-04
- **Связано:** [ADR-0002](0002-memory-model.md), [ADR-0003](0003-borrowing-model.md), [ADR-0005](0005-concurrency.md), [ADR-0006](0006-compiler-architecture.md); [ARCHITECTURE.md](../ARCHITECTURE.md) §4, §8; аудит §3.1, §5.6; вопрос Q-32

## Проблема

Решено: трассирующего GC в 1.0 нет ([ADR-0002](0002-memory-model.md)). Но нужна возможность добавить его позже без фундаментальной перестройки языка.

Что может закрыть этот путь:
- семантика, обещающая то, что GC нарушит (например, «деструктор вызывается всегда»);
- представление программы в компиляторе, где виды указателей уже неразличимы;
- runtime без точек, через которые GC мог бы узнать о потоках и корнях;
- стандартная библиотека, которую пришлось бы переписывать;
- экосистема, которая раскалывается, как только GC появляется (опыт D).

## Возможные варианты

- **А.** Ничего не делать сейчас: понадобится GC — тогда и разберёмся.
- **Б.** Заложить GC в 1.0 «на всякий случай»: заглушки в runtime, барьеры записи, safepoint.
- **В.** Зафиксировать сейчас ограничения дизайна, которые почти ничего не стоят, но сохраняют путь к GC; сам GC не проектировать, пока нет данных.

## Рекомендуемое решение

Вариант **В**. Восемь ограничений, которые соблюдаются с первого дня:

1. **Утечки безопасны.** Безопасный код не опирается на гарантированный вызов деструктора (уже следует из ADR-0002).
2. **GC-куча — отдельный регион.** Будущий GC — это отдельная куча (`GcHeap`) со своим типом указателя (`Gc<T>`), а не свойство любого типа. Раскладка обычных типов и `Shared` от GC не зависит.
3. **Допуск в GC-кучу — через автотрейт** (рабочее название `GcSafe`): только типы без деструкторов с побочными эффектами, без заимствований и без владения ресурсами. Механизм автотрейтов нужен и сейчас — для `Send`/`Sync`.
4. **Виды указателей сохраняются в KIR до кодогенерации:** владеющий, `Shared`, `Weak`, сырой, заимствование. GC-указатель добавится как новый вид в KIR и backend; фронтенд не меняется.
5. **Корни — через явные дескрипторы, без сканирования стека.** Это работает в WebAssembly, где стек сканировать нельзя, и не требует от LLVM карт стека. Карты стека (statepoint) — возможная оптимизация позже, изолированная в backend.
6. **Сырые указатели получаются только явно** (`addressOf` в `unsafe`), без неявных преобразований. Перемещающий сборщик сможет потребовать закрепления объекта на это время. Заимствования второго класса короткие и ограничены областью видимости, поэтому закрепление на время заимствования дёшево.
7. **Потоки создаются через runtime std.** Это точка регистрации потоков для будущего GC. GC-куча по умолчанию привязана к потоку, так что останавливать все потоки программы не понадобится.
8. **Стандартная библиотека не использует GC-типы в публичных API.** GC остаётся необязательным, экосистема не раскалывается.

Дополнительно: компилятор умеет перечислять поля-указатели любого типа — это то же знание, что нужно для `derive`. Его достаточно, чтобы генерировать функции обхода объектов для будущего сборщика.

Сам сборщик — отдельное решение не раньше конца этапа 2 и только по данным (условия — аудит §5.6). Первой стоит рассмотреть более дешёвую альтернативу — сборщик циклов для `Shared` (как ORC в Nim): ациклические данные по-прежнему освобождаются детерминированно, а сборщик находит только циклы.

## Причины выбора

- Шесть из восьми ограничений уже следуют из принятых решений; дополнительная цена близка к нулю.
- Вариант Б нарушает принцип предсказуемой производительности (барьеры и safepoint в коде, который GC не использует) и правило «три хорошие возможности лучше десяти».
- Вариант А рискует закрыть путь случайными решениями — например, ранним стиранием видов указателей в IR.

## Последствия

- GC, если появится, будет «островом»: объекты в GC-куче живут по своим правилам, остальной язык не меняется.
- Типы с деструкторами в GC-кучу не попадут: ресурсы по-прежнему управляются RAII.
- Код, использующий GC, явно помечен типами `Gc<T>` и `GcHeap`.

## Риски

- **«Остров» окажется неудобным для UI** — главного сценария, ради которого GC может понадобиться. Снижение: пересматривать вместе со стратегией GUI; прототип до решения.
- **Корни через дескрипторы медленнее карт стека.** Снижение: карты стека — оптимизация в backend, если измерения покажут необходимость.

## Статус и условия пересмотра

Предлагается. Соблюдение ограничений 1–8 проверяется при ревью каждого ADR и каждого изменения KIR и runtime.
