# ADR-0010. Синтаксическая основа

- **Статус:** принято как основа спецификации (05.11.2026); точечные правки — до точки G0
- **Дата:** 2026-11-05
- **Связано:** [SYNTAX_SKETCH.md](../SYNTAX_SKETCH.md), [CORPUS_REVIEW.md](../CORPUS_REVIEW.md), [ADR-0003](0003-borrowing-model.md), [ADR-0004](0004-types-and-polymorphism.md); вопросы Q-07, Q-14, Q-18, Q-26, Q-39

## Проблема

Синтаксис — главный носитель удобства языка. Kotlin — хорошая отправная точка, но KENOX — системный язык с владением. Часть конструкций Kotlin в нём не работает или противоречит другим решениям: неявные ссылки, `?` против `try`, фигурные скобки как блок и как замыкание. Часть нужно добавить: режимы параметров, `unsafe`, границу с C.

Условие инициатора (05.11.2026): KENOX не должен становиться копией Kotlin — нужен собственный узнаваемый синтаксис, сочетающий читаемость, лаконичность и удобство системного программирования.

## Возможные варианты

- **А.** Копия поверхности Kotlin с добавлением системных конструкций.
- **Б.** Поверхность Rust с косметическими упрощениями.
- **В.** Собственный синтаксис: основа Kotlin (`fun`, `val`/`var`, `имя: Тип`, trailing-лямбды, `?.`, `?:`) плюс системная точность и устранённые конфликты.

## Рекомендуемое решение

Вариант **В** — по [эскизу](../SYNTAX_SKETCH.md). Ключевые решения:

1. Условия без скобок, фигурные скобки обязательны.
2. `match` с ветками `->`, варианты перечислений через точку (`.Circle(r)`); проверка полноты.
3. `x is .V(a)` — проверка образца с привязками; `if val`, `while val`, `if inout`.
4. Строковые шаблоны `"{x}"`; сырые строки `r"…"`; литерал имеет тип `String` без выделения памяти (Р-4).
5. Только явные диапазоны `..<` и `..=`.
6. Передача ошибки — `try выражение` (Р-1); безопасный вызов — `?.`, значение по умолчанию — `?:`.
7. Режимы параметров: по умолчанию заимствование, `inout` (на месте вызова `&x`), `consume`.
8. Одна конструкция `extend` для расширений и реализаций трейтов; делегирование `by self.поле` пересылает только обязательные методы (Р-8).
9. `{ … }` в позиции выражения — замыкание; в ветке `match` — блок; отдельный блок — `do { … }` (Р-2).
10. `ref` и `consume` как выражения; результаты-заимствования `ref T` и `inout T` (Р-12, Р-16).
11. `some Трейт` — непрозрачный тип результата (Р-11).
12. Обязательный `self.` в методах; функция без `self` в теле типа — статическая.
13. Атрибуты `@…`; видимость по умолчанию — внутри пакета, `pub`, `private`.
14. Целое по умолчанию — `Int` (64 бита), оно же тип длин и индексов (Р-25).
15. Передача владения на месте вызова не помечается: перемещение видно в сигнатуре, повторное использование — ошибка компиляции; пометка `consume x` разрешена, но не обязательна (Р-3, Q-39, вариант А — утверждён 05.11.2026).

## Причины выбора

- Основа Kotlin узнаваема и читаема для широкой аудитории.
- Каждое отличие от Kotlin решает конкретную проблему: системную точность (`inout`, `&`, `ref`, `consume`, `@repr`), однозначность (`try`, `do`, `..<`/`..=`) или единообразие (`extend`, `is`).
- Корпус из 44 примеров написан без нарушений этих правил ([CORPUS_REVIEW.md](../CORPUS_REVIEW.md)).

## Последствия

- Грамматика (шаг 0.3) должна разрешить: перевод строки как конец инструкции, угловые скобки обобщений рядом со сравнениями, лямбды против блоков.
- Каждая форма сахара должна сводиться к небольшому ядру ещё до проверки типов.
- Корпус примеров становится тестами синтаксиса на этапе 1.

## Риски

- **Слишком много сахара** (`if val`, `is`, `?.`, `?:`, `do`, trailing-лямбды). Снижение: сахар допускается, только если он рассахаривается в ядро и встречается в корпусе.
- **Неоднозначности грамматики** обнаружатся только при формальном описании. Снижение: шаг 0.3; точечный пересмотр синтаксиса до начала этапа 1.

## Статус и условия пересмотра

Принято 05.11.2026 как основа спецификации, включая вариант А для Р-3. Окончательно — в точке G0: грамматика шага 0.3 может потребовать точечных правок, и каждая из них оформляется через этот ADR.
