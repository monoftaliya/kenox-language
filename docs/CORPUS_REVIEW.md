# KENOX — анализ корпуса примеров (эксперимент E-1)

> Версия 0.2 · 5 ноября 2026 · Этап 0, шаг 0.2 · Статус: утверждено 05.11.2026
> Корпус — [examples/](../examples/README.md); синтаксис — [SYNTAX_SKETCH.md](SYNTAX_SKETCH.md); решения — [ADR/](ADR/README.md).

## 1. Итог

1. **Модель выдержала корпус.** 44 примера по 12 темам написаны в рамках модели памяти без её нарушений. `unsafe` понадобился только там, где он ожидаем: ручная память и вызовы C — 5 файлов из 48.
2. **Упрощённые заимствования работают.** Аннотация источника заимствования понадобилась один раз на 44 примера. Аннотаций времени жизни в структурах нет совсем.
3. **Найдена одна существенная проблема модели — коллекции и итераторы, содержащие заимствования** (Р-10). Без решения не работают ленивые цепочки итераторов, если замыкание захватывает локальную переменную. Предлагаемое решение — «условная невыходящесть» — безопасности не ослабляет, но его нужно формализовать на шаге 0.4.
4. **Найдены и устранены три синтаксических конфликта**, которые сделали бы язык противоречивым: `?` в Rust против `?.` в Kotlin (решение — `try`), фигурные скобки как блок или как замыкание (решение — `do { }`), тип строкового литерала (решение — `String` без выделения памяти).
5. **Наследование не понадобилось.** Повторное использование кода закрыли методы трейтов по умолчанию, делегирование `by`, обобщения и расширения. Одно правило делегирования нужно закрепить (Р-8).

Решения из раздела 9 утверждены 05.11.2026.

## 2. Что и как проверялось

- **Объём:** 44 примера по 12 темам из вашего списка, 48 файлов `.kenox` (пакеты из раздела 11 состоят из нескольких модулей), 4 файла на C, 4 манифеста `kenox.toml`.
- **Соответствие эскизу.** Скрипт ищет конструкции других языков: `fn`, `=>`, `let`, `impl`, `mut`, `when`, `this`, `::`, скобки вокруг условий, диапазоны `..` без `<` или `=`, `?` для передачи ошибки, `$` в строках, `->` вместо `:` в типе результата. Результат — **0 нарушений**. Сам скрипт проверен на файле с намеренными ошибками: все они найдены. С шага 0.1 эта проверка — часть `cargo test` (инструмент `tools/repo-check`).
- **C-код** из раздела 12 проверен компилятором clang 18 (`-Wall -Wextra`) — без предупреждений.
- **Модель памяти** проверялась чтением: каждое заимствование, перемещение и изменение сверено с правилами эскиза. Найденные расхождения либо исправлены в примерах, либо вынесены в список Р-N.

**Ограничения анализа.** Компилятора нет, примеры не выполнялись. Модель и примеры писал один автор, поэтому возможна «слепота автора». Рекомендую независимое ревью по протоколу [ADR-0027](ADR/0027-ai-assisted-development.md): передать ChatGPT эскиз и корпус и попросить найти программу, которую модель должна отвергнуть, но пропустит.

## 4. Гарантии безопасности

Ваше условие: упрощённая модель не должна допускать некорректного доступа к памяти, use-after-free и гонок данных в безопасном коде. Как модель это обеспечивает и где это видно в корпусе:

| Угроза | Чем предотвращается | Где показано |
|---|---|---|
| Использование после освобождения | Перемещённое значение недоступно; заимствование не переживает владельца; заимствование нельзя сохранить в поле или коллекцию; результат-заимствование привязан к источнику | 09-01, 05-01, 09-03 (✗) |
| Висячая ссылка на элемент коллекции | Пока элемент заимствован, коллекцию нельзя изменить | 07-01, 09-02, 09-03 (✗) |
| Изменение коллекции во время обхода | Цикл заимствует коллекцию | 07-01 (✗) — в Kotlin это исключение во время выполнения |
| Псевдонимы изменяемых данных | Два `inout` к одному месту запрещены | 09-02 (✗) |
| Выход за границы | Проверка границ; при нарушении — паника, а не чтение чужой памяти | 06-03 |
| Null | `null` существует только у `T?` и требует проверки | 08-03, 10-* |
| Неинициализированная память | Компилятор проверяет инициализацию; сырая память — только в `unsafe` | 09-07 (✗) |
| Недопустимое значение перечисления из C | Принимать `CInt` и проверять `tryFrom` | 12-02 (Р-24) |
| Гонки данных | `Send`/`Sync`; `Cell` не `Sync`; общее изменяемое состояние — только через `Mutex` | 09-08 (✗ ×2) |
| Повторный вход в `Cell.update` | Проверка во время выполнения — паника, а не повреждение данных | 09-05 |

**Что модель не гарантирует** (как и Rust): утечки памяти при циклах `Shared` (09-05), взаимоблокировки, логические гонки уровня приложения, паники, корректность кода внутри `unsafe`.

**Найденная дыра — в `unsafe`, а не в безопасном коде.** Висячий указатель от временной `CString` (Р-23) сейчас возможен внутри `unsafe`. Предложено превратить его в ошибку компиляции: `ptr()` должен возвращать невыходящее представление, привязанное к строке.

**Что нужно формализовать** на шаге 0.4, чтобы гарантии были доказаны, а не только продемонстрированы: условная невыходящесть (Р-10), результаты-заимствования (Р-12), общий тип ветвей (Р-15), режимы привязок (Р-17), двухфазные заимствования (09-02), режимы захвата в замыканиях (02-03).

## 6. Синтаксис: свой, а не копия Kotlin

**Взято из Kotlin:** `fun`, `val`/`var`, `имя: Тип`, trailing-лямбды, `it`, `?.`, `?:`, `null`, именованные аргументы, функции-выражения.

**Своё:**
- условия без скобок;
- `match` с ветками `->` и вариантами через точку (`.Circle(r)`);
- `is` как проверка образца с привязками;
- строковые шаблоны `"{x}"`;
- только явные диапазоны `..<` и `..=`;
- `try` для передачи ошибки;
- режимы параметров `inout`/`consume` и `&` на месте вызова;
- одна конструкция `extend` для расширений и реализаций трейтов;
- `do { }` для блоков;
- `ref`/`consume` как выражения;
- `some` для непрозрачных типов;
- атрибуты `@…`;
- обязательный `self.`.

Полная таблица отличий — раздел 20 [эскиза](SYNTAX_SKETCH.md).

### Р-3. Видимость передачи владения

`deposit(&acc, 50)` показывает изменение, а `close(acc)` не показывает, что `acc` больше недоступна.

- **Вариант А (утверждён 05.11):** как в Rust — перемещение неявное, его видно в сигнатуре. Компилятор даёт понятную ошибку с местом перемещения, IDE показывает подсказку. Пометка `consume x` разрешена, но не обязательна.
- **Вариант Б:** обязательный `consume x` для именованных переменных. Всё видно, но становится шумно в самом частом коде — например, при сборке структур из локальных переменных: `User(name = consume name, email = consume email)`.

Ошибка «использование после перемещения» в обоих вариантах ловится при компиляции, поэтому выбор касается читаемости, а не безопасности.

### Р-10. Условная невыходящесть

Правило ADR-0003 «заимствование нельзя положить в коллекцию» оказалось слишком грубым. Ленивый итератор `sales.iter().filter { it.amount >= threshold }` хранит замыкание, которое заимствует `threshold`. По буквальному правилу такой итератор — запрещённая структура с заимствованием. То же с `List<str>` из `split`, с `partition` и `groupBy`.

**Предложение:** невыходящесть — структурное свойство типа, которое выводится, как `Send`. Тип, содержащий заимствование, сам становится невыходящим: его можно держать в локальной переменной, передавать и возвращать с зависимостью от источника, но нельзя сохранить в выходящем месте (поле обычной структуры, `Shared`, глобальная переменная, выходящее замыкание).

Это не ослабляет безопасность: заимствование по-прежнему не может пережить источник. Похожий механизм есть в Swift (невыходящие типы) и C# (`ref struct`). Заодно решается Р-18: лексер сможет хранить `str` без копии и сам станет невыходящим.

Цена — сложнее проверка типов, обобщения должны учитывать признак невыходящести. Это главный пункт для формальной модели на шаге 0.4.
