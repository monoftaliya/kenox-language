## P0 — нужен ответ сейчас

Четыре решения из главы 1 спецификации ([spec/01-lexical.md](../spec/01-lexical.md), раздел 1.9). Они утверждаются вместе с главой — слиянием её pull request; возражения — комментарием в pull request или в чате.

### Q-42. Ключевые слова: жёсткие или контекстные *(глава 1)*
- **Варианты:** (А) все ключевые слова жёсткие, а имя, совпадающее с ключевым словом, пишется в обратных кавычках: `` `type` `` — как в Kotlin и Swift; (Б) часть слов (`type`, `ref`, `some`, `by`, `where`, `inout`, `consume`, `escaping`) — контекстные и годятся как имена вне своих конструкций; (В) все жёсткие, без обхода.
- **Рекомендация:** А. Грамматика и инструменты проще, смысл слова не зависит от места. Обратные кавычки нужны редко — например, для поля `type` из C-структуры.

### Q-43. Битовые операции *(глава 1)*
- **Варианты:** (А) операторы `&` `|` `^` `~` `<<` `>>` и составные присваивания — как в C, Rust и Swift; (Б) инфиксные функции `and` `or` `xor` `shl` `shr` и метод `inv()` — как в Kotlin.
- **Рекомендация:** А. Ниша 1.0 — системные утилиты, флаги C-библиотек, вычисления: код читается так же, как заголовки C. Приоритет битовых операций будет выше сравнений, как в Rust и Swift (глава 2), — это убирает известную ловушку C `x & MASK == 0`. Префиксный `&` остаётся пометкой `inout`: двоичный и префиксный знак различаются по месту, как `-`. Побитовое «не» — `~`, а `!` остаётся только логическим.

### Q-44. Отступ в многострочных строках *(глава 1)*
- **Варианты:** (А) отступ закрывающих кавычек убирается из каждой строки при компиляции — как в Swift, Java и C#; (Б) текст хранится как есть, отступ убирают вызовом `.trimIndent()` — как в Kotlin.
- **Рекомендация:** А. Нет затрат во время выполнения, отступ нельзя забыть убрать. Следствие: в примере 01-03 вызов `.trimIndent()` больше не нужен — он убран в этом же pull request.

### Q-45. Строка, начинающаяся с точки *(глава 1)*
- **Суть:** в Kotlin строка, начинающаяся с `.`, продолжает цепочку методов. В KENOX с точки начинаются и образцы веток `match` (`.Circle(r) -> …`), поэтому нужно правило.
- **Варианты:** (А) строка с `.` продолжает выражение везде, кроме уровня веток `match`, где `.Вариант` начинает новую ветку; (Б) строка с `.` никогда не продолжает выражение — длинная цепочка пишется в скобках или с точкой в конце строки.
- **Рекомендация:** А. Цепочки итераторов — основная идиома корпуса, и они остаются привычными. Цена: многострочная цепочка в теле ветки `match` берётся в скобки, а инструкция в блоке не может начинаться с `.Вариант` — компилятор подскажет.

## P1 — до завершения MVP

### Q-08. Неявное или явное копирование `Shared`
Копирование `Shared` увеличивает счётчик ссылок. **Рекомендация:** явное (`share()`) — так и написан корпус; неявное — только у будущего `class`.

### Q-09. Один тип `Shared` или два
**Рекомендация:** два типа — `Shared` (атомарный, для потоков) и `LocalShared` (для одного потока), как в корпусе; пересмотр по данным E-2.

### Q-10. Переполнение: ловушка во всех профилях
**Рекомендация:** да, плюс явные операции заворачивания и насыщения ([ADR-0009](ADR/0009-base-types-null-safety.md)). Пересмотр — только для профиля Performance и только по данным E-3.

### Q-11. Тип индексов и длин коллекций
**Рекомендация изменена по итогам корпуса (Р-25):** знаковый `Int` (64 бита) для длин, индексов и обычной арифметики; `USize` — только на границе с C. В корпусе преобразование понадобилось один раз — при вызове `qsort`.

### Q-12. Раскрутка стека при панике
С потоками в 1.0 перехват паники на границе потока важен для серверов. **Рекомендация:** в MVP — аварийное завершение; до этапа 3 решить о раскрутке с перехватом на границах потоков (ADR-0020).

### Q-13. Когерентность трейтов
**Рекомендация:** строгое правило «сироты» для библиотек, ослабленное — для конечных приложений (пример 04-04).

### Q-14. Модули, пакеты и имена std
**Рекомендация:** файл = модуль, путь модуля — от `src/`; имена в нижнем регистре через точку (`std.collections`). Так написан корпус (пакеты 11-01 и 11-02).

### Q-15. Windows: MSVC или GNU ABI
**Рекомендация:** MSVC — Tier 1. Ваша основная среда — Windows 11, а стандартный инструментарий Rust на Windows тоже использует MSVC: одна установка Visual Studio Build Tools обслужит и сборку компилятора, и программы на KENOX. Решается на вехе 1f.

### Q-16. Имя, расширение файлов, товарный знак
«Kenox» использовался как бренд фотоаппаратов Samsung. **Рекомендация:** проверить товарные знаки до публичного анонса языка; расширение — `.kenox`.

### Q-36. Границы вычислений в 1.0
**Рекомендация:** CPU одной машины — SIMD-типы, параллельные итераторы, контроль выравнивания, `noalias` для `inout` после формализации алиасинга. GPU, MPI и ослабленная математика по умолчанию — не в 1.0.

## P2 — до соответствующего этапа

### Q-18. Синтаксис явного источника заимствования *(шаг 0.3)*
**Предложение по итогам корпуса:** атрибут `@borrows(a, b)`; у методов источник по умолчанию — `self`. В корпусе аннотация понадобилась один раз (09-03).

### Q-19. Регионные ссылки для арен *(этап 2)*
**Рекомендация:** не вводить без данных E-7; пока принадлежность дескриптора арене проверяется во время выполнения (09-06).

### Q-20. Деструкторы в аренах *(этап 2)*
**Рекомендация:** два вида арен — «быстрая» без деструкторов и «полная» с деструкторами; вид выбирается явно.

### Q-21. `defer` *(этап 2)*
**Рекомендация:** в корпусе случаев не нашлось — не добавлять.

### Q-22. Линейные типы *(этап 2)*
**Рекомендация:** не в 1.0; вместо этого — предупреждение о незакрытом ресурсе с методом `close()` (Р-22).

### Q-26. Перегрузка функций *(шаг 0.3)*
**Рекомендация:** полный запрет; именованные аргументы и значения по умолчанию. Корпус написан без перегрузки.

### Q-37. Импорт C-заголовков *(этап 3)*
**Рекомендация:** отдельный инструмент на libclang; в 1.0 — если успеет, иначе 1.x ([ADR-0013](ADR/0013-ffi.md)).

### Q-38. Формат описания экспортируемого API *(до этапа 3)*
**Рекомендация:** версионируемый JSON: типы, функции, владение, nullable, правила освобождения памяти. Первый потребитель — генератор C-заголовков (пример 12-04).

### Q-41. Сборка C-исходников из `kenox.toml` *(новый, этап 3; Р-26)*
**Рекомендация:** секция `[native]` — собирать C-файлы пакета тем же clang, что и KENOX (пример 12-02). Небольшая возможность, заметно упрощающая работу с C.

- **Детальный API стандартной библиотеки** после этапа 4.
- **Модель управления проектом** — до появления внешних участников.
- **Стратегия UI** — после 1.0 (Q-31).
