# 3. Имена, модули и видимость

> Глава спецификации ядра · Версия 0.1 · 5 ноября 2026 · Черновик — ждёт утверждения · Общие соглашения — [README](README.md)
>
> Глава определяет, из чего состоит программа — пакеты и модули, — где действует каждое имя, как по имени находится объявление, что делает импорт и кому видно объявление. Глава описывает ядро 0.1; о библиотеках, зависимостях и расширениях чужих типов здесь сказано только то, без чего правила пришлось бы менять позже. Решения, которых не было в эскизе, — в разделе 3.11; пять заметных из них требуют утверждения вместе с главой. Сводка решений — [ADR-0011](../docs/ADR/0011-modules-names-visibility.md).

Термины главы:

- **Объявление** вводит имя: функция, структура, перечисление, трейт, константа, псевдоним типа, функция блока `extern`, импорт, обобщённый параметр, параметр функции, локальная привязка.
- **Область действия** имени — часть программы, где имя можно написать без уточнения.
- **Видимость** — где объявление можно назвать: в файле, в пакете или везде (раздел 3.6).
- **Член типа** — поле, метод, статическая функция, константа, ассоциированный тип или вариант перечисления. К членам обращаются через точку.

## 3.1 Пакеты

**[name.package]** Пакет — единица сборки: каталог с файлом `kenox.toml` и каталогом `src/` с исходными файлами. Для языка в `kenox.toml` важны два поля раздела `[package]`: имя `name` и вид `kind`. Остальные поля описывает документация инструмента `kenox`.

**[name.package.name]** Имя пакета подчиняется правилам имени модуля ([name.module.name]): строчные латинские буквы, цифры и `_`, первая — буква. Так имя пишется одинаково в `kenox.toml` и в импорте. Имя `std` занято стандартной библиотекой (раздел 3.9).

**[name.package.kind]** Вид пакета определяет его корневой модуль: у исполняемой программы (`kind = "bin"`) это `src/main.kenox`, у библиотеки (`lib`, `staticlib`, `dylib`) — `src/lib.kenox`.

**[name.package.core]** Программа ядра 0.1 — один пакет вида `bin` и стандартная библиотека. Библиотеки и зависимости между пакетами — вне ядра 0.1. Пути в другие пакеты всё же описаны сразу (раздел 3.9): так же импортируется `std`.

## 3.2 Модули

**[name.module.file]** Модуль — один файл `.kenox` в каталоге `src/` или в его подкаталогах. Путь модуля — путь файла относительно `src/` без расширения, в котором `/` заменена точкой: `src/model/item.kenox` — модуль `model.item`. Объявлять модуль в коде не нужно: файл и есть модуль.

**[name.module.dir]** Каталог внутри `src/` — пространство имён, а не модуль: объявлений в нём нет, только модули и подкаталоги. Каталоги без файлов `.kenox` и файлы с другими расширениями в программу не входят.

**[name.module.name]** Имя модуля (имя файла без `.kenox`) и имя каталога состоят из строчных латинских букв, цифр и `_`, начинаются с буквы и не совпадают с ключевым или зарезервированным словом ([lex.keyword.list], [lex.keyword.reserved]). Другое имя — ошибка. Такие имена одинаково ведут себя в файловых системах Windows, macOS и Linux: не мешают ни регистр букв, ни разные формы записи символов Unicode.

**[name.module.clash]** Файл `a.kenox` и каталог `a/` в одном каталоге — ошибка: путь `a` должен называть что-то одно.

**[name.module.root]** Корневой модуль ([name.package.kind]) — вход в пакет. Пути внутри своего пакета у него нет, поэтому модули пакета его объявлений не импортируют: зависимости идут от корневого модуля к остальным, а не обратно. Другим пакетам видны открытые объявления корневого модуля библиотеки (раздел 3.9). Если в `src/` лежат оба файла, `main.kenox` и `lib.kenox`, тот, что не стал корневым, — ошибка.

```text
inventory/                    name = "inventory", kind = "bin"
├── kenox.toml
└── src/
    ├── main.kenox            корневой модуль
    ├── report.kenox          модуль report
    └── model/                каталог: пространство имён model
        ├── item.kenox        модуль model.item
        └── stock.kenox       модуль model.stock
```

## 3.3 Области действия

**[name.scope.nest]** Области действия вложены друг в друга. Изнутри наружу:

1. блок — локальные привязки и привязки образцов;
2. функция — её параметры;
3. объявление — обобщённые параметры функции, затем типа, трейта или `extend`, внутри которого она объявлена;
4. модуль — объявления верхнего уровня этого файла и его импорты;
5. универсальная область — встроенные типы и прелюдия (раздел 3.8).

**[name.scope.module]** Объявление верхнего уровня действует во всём своём файле независимо от порядка: функция вызывает функцию, объявленную ниже, тип ссылается на тип, объявленный ниже. В другой файл объявление попадает только через импорт.

**[name.scope.local]** Локальная привязка (`val`, `var`, `inout`) действует со следующей инструкции до конца своего блока. В собственном инициализаторе она ещё не видна.

**[name.scope.pattern]** Привязки образца действуют: в ветке `match` — в её условии и теле; в `for` — в теле цикла, но не в выражении после `in`; в `val` с образцом — как локальная привязка ([name.scope.local]). В `if val` и `while val` (вне ядра 0.1) — в теле, у `if` — только в первой ветке. Где действуют привязки после `is`, определяет глава 6.

**[name.scope.generic]** Обобщённый параметр действует во всём объявлении: в сигнатуре, условиях `where` и теле. Параметры типа, трейта и `extend` действуют во всех их членах. Повторить имя обобщённого параметра — в том же списке или в объявлении внутри — ошибка: `T` метода легко спутать с `T` его типа.

**[name.scope.self]** `self` — параметр-получатель ([syn.fun.self]); действует в теле метода, который его объявил. `Self` действует в теле типа, трейта и `extend` и означает тип, к которому относится член, а в трейте — тип, реализующий трейт. В других местах `self` и `Self` — ошибка.

Параметры замыканий и неявный параметр `it` описываются вместе с замыканиями (вне ядра 0.1).

```kenox
fun main() {
    println(square(4))          // ✓ square объявлена ниже: порядок верхнего уровня не важен
}

fun square(x: Int): Int = x * x

struct Stack<T> {
    items: List<T>

    fun peek(self): ref T? = self.items.last()      // T — параметр Stack
    // ✗ [name.scope.generic] fun first<T>(self): T? — имя T уже занято параметром Stack
}
```

## 3.4 Поиск имени

**[name.lookup.order]** Имя без уточнения ищется в областях действия изнутри наружу ([name.scope.nest]); находится ближайшее объявление. Если имени нет ни в одной области — ошибка.

**[name.lookup.one]** Пространство имён одно: типы, функции, константы, модули, параметры и переменные не различаются. Поэтому в одной области одно имя означает одно объявление, и повтор имени в одной области — ошибка: два объявления верхнего уровня, объявление и импорт, два импорта, два параметра одной функции. Перегрузки функций нет (Q-26): разные операции называются по-разному.

**[name.lookup.hide]** Объявление внутренней области скрывает одноимённое объявление внешней до конца своей области. Объявления и импорты модуля скрывают имена универсальной области без ошибки и без предупреждения: поэтому новое имя в прелюдии не ломает существующие программы. Для параметров и локальных привязок действует ограничение [name.local.unique].

**[name.local.unique]** Параметр функции, локальная привязка и привязка образца не могут повторять имя другого параметра, локальной привязки, привязки образца или обобщённого параметра, видимых в этом месте, — ни в том же блоке, ни во вложенном. Это ошибка (Q-46). В соседнем блоке и после конца области прежней привязки имя снова свободно. В одном образце имя привязывается один раз; в альтернативах через `|` — по одному разу в каждой (глава 6). Заполнитель `_` ничего не объявляет и может повторяться. Скрывать имена модуля и универсальной области можно.

Вместе с [syn.pat.binding] это значит: одиночное имя в образце не может тихо подменить переменную. Совпадение имени привязки с переменной или параметром — ошибка, с константой — предупреждение [syn.pat.binding-warning]. Видимая константа в том правиле — константа в области действия: объявленная в файле или импортированная.

**[name.lookup.qualified]** В записи `a.b` сначала находится `a`. Если `a` — модуль, введённый импортом, то `b` — объявление этого модуля: `fs.readText(…)`, `fs.IoError`. Если `a` — тип, в том числе обобщённый параметр или `Self`, то `b` — статический член типа (статическая функция, константа, ассоциированный тип или вариант): `Item.new(…)`, `Float64.PI`, `T.zero()`, `Self.Item`, `Shape.Circle`. Если `a` — значение, то `b` — поле или метод (глава 5). В каждом случае `b` должно быть видно в этом месте (раздел 3.6).

**[name.lookup.members]** Члены типа в области действия не входят: без уточнения поле, метод или константа типа не находятся даже в теле самого типа. Поле и метод называются через `self.`, статическая функция и константа — через `Self.` или имя типа. Поэтому параметр метода не спорит с полем: `self.value = value`.

**[name.lookup.special]** В областях действия не ищутся: имя после точки ([name.lookup.qualified]); `.Имя` без левой части — член ожидаемого типа ([syn.implicit-member], глава 5); имена полей при создании значения и в образцах; имена аргументов при вызове; имена атрибутов. Набор атрибутов и смысл их аргументов задают главы, где атрибуты описаны; неизвестный атрибут — ошибка.

**[name.cycle]** Константа и псевдоним типа не могут зависеть от себя — прямо или через другие константы и псевдонимы: `const A = B + 1` вместе с `const B = A` — ошибка. Функции и типы ссылаться друг на друга могут; какие рекурсивные типы допустимы, определяет глава 4.

```kenox
fun area(r: Float64): Float64 = Float64.PI * r * r
// ✗ [name.lookup.one] fun area(w: Float64, h: Float64): Float64 = w * h — перегрузки нет: имя area занято

struct Point { x: Int, y: Int }
// ✗ [name.lookup.one] fun Point(x: Int): Point = Point(x = x, y = 0) — имя Point занято типом

struct Counter {
    value: Int

    fun increment(inout self) {
        self.value += 1
        // ✗ [name.lookup.members] value += 1 — поле называется через self
    }

    fun reset(inout self, value: Int) {
        self.value = value                  // ✓ параметр value не спорит с полем
    }
}
```

```kenox
fun total(prices: List<Int>): Int {
    var sum = 0
    for price in prices {
        // ✗ [name.local.unique] val sum = sum + price — sum уже объявлена; имелось в виду sum += price
        sum += price
    }
    return sum
}

fun verdict(code: Int, expected: Int): String = match code {
    // ✗ [name.local.unique] expected -> "совпало" — имя занято параметром; сравнение пишется условием ветки
    n if n == expected -> "совпало"
    _ -> "другое"
}

fun twice(xs: List<Int>) {
    for x in xs { println(x) }
    for x in xs { println(x * 2) }          // ✓ прежняя x уже не видна
    val print = "отчёт"                      // ✓ локальное имя скрывает функцию прелюдии
    println(print)
}
```

## 3.5 Импорт

**[name.import.path]** Путь импорта ([syn.import.form]) начинается с имени модуля или каталога верхнего уровня своего пакета (`report`, `model`) или с имени другого пакета (`std`, раздел 3.9). Относительных путей нет. Каждое следующее имя ищется в том, что названо предыдущим: в каталоге — модули и подкаталоги, в модуле — объявления верхнего уровня и реэкспорты. Группа `import p.{a, b}` означает то же, что `import p.a` и `import p.b`.

**[name.import.target]** Импорт называет модуль или объявление верхнего уровня модуля. Каталог, пакет целиком, корневой модуль своего пакета и член типа (вариант, статическую функцию, константу типа) импортировать нельзя — ошибка.

**[name.import.binds]** Импорт вводит в область своего модуля последнее имя пути: `import std.fs` вводит `fs`, `import model.item.Item` — `Item`. Другим файлам этот импорт не виден.

**[name.import.only]** Объявление другого модуля называется только через импорт. Имена пакетов, каталогов и модулей, не введённые импортом, в выражениях и типах не ищутся: `std.fs.readText(path)` без `import std.fs` — ошибка. Так по строкам импорта видно, откуда пришло каждое имя файла.

**[name.import.visible]** Импортировать можно только видимое объявление (раздел 3.6): из другого файла своего пакета — объявленное без `private`, из другого пакета — объявленное с `pub`. Модуль импортировать можно всегда: видимость проверяется у его объявлений.

**[name.import.unused]** Импорт, который в файле не используется, — предупреждение. Импорт используется, если его имя встречается в файле или через него найден метод трейта ([name.trait.scope]). `pub import` не проверяется: его используют те, кто импортирует реэкспорт.

**[name.import.reexport]** `pub import` ([syn.import.pub]) работает как `import` и вдобавок делает импортированные имена открытыми объявлениями своего модуля: их можно импортировать через путь этого модуля. Реэкспортировать можно только объявления с `pub` — иначе ошибка: реэкспорт не расширяет видимость. Модули не реэкспортируются.

**[name.import.cycle]** Модули одного пакета могут импортировать друг друга взаимно: порядок модулей в пакете не важен.

```kenox
import std.fs                          // модуль: дальше fs.readText(…) и fs.IoError
import std.collections.{Map, Set}      // объявления модуля
import model.item.Item                 // свой пакет: файл src/model/item.kenox
// ✗ [name.import.target] import model — model — каталог, а не модуль
// ✗ [name.import.target] import std — пакет целиком не импортируется
// ✗ [name.import.target] import model.item.Item.new — путь не заходит внутрь типа
// ✗ [name.module.root] import main.Config — у корневого модуля нет пути внутри пакета

fun load(path: str): Result<String, fs.IoError> = fs.readText(path)
fun names(items: Slice<Item>): Set<String> { … }
fun totals(items: Slice<Item>): Map<String, Int> { … }
// ✗ [name.lookup.one] fun fs(): Int = 0 — имя fs уже введено импортом
// ✗ [name.import.only] fun home(): String? = std.env.get("HOME") — имя std не введено импортом
```

```kenox
import std.fs
import std.env                         // ⚠ [name.import.unused] env в файле не используется

fun load(path: str): Result<String, fs.IoError> = fs.readText(path)
```

Реэкспорт — корневой модуль библиотеки `textstats` (пример 11-02):

```kenox
pub import counting.{wordCount, stats, Stats}     // потребитель пишет import textstats.wordCount
// ✗ [name.import.reexport] pub import counting.countLetters — у countLetters нет pub: реэкспорт не расширяет видимость

pub fun version(): String = "0.1.0"
```

## 3.6 Видимость

**[name.vis.levels]** Видимость задаёт, где объявление можно назвать:

| Запись | Где видно объявление |
|---|---|
| `private` | только в файле, где оно написано |
| без модификатора | во всём пакете |
| `pub` | везде, в том числе в других пакетах |

**[name.vis.place]** Видимость пишется перед объявлением верхнего уровня, кроме `extend`, а также перед полем, функцией и константой в теле структуры или перечисления и в `extend Тип { … }` без трейта. Видимость перед блоком `extern` относится ко всем его функциям. Перед `extend`, перед членами трейта и членами реализации трейта видимость писать нельзя — ошибка: члены трейта видны там же, где трейт, а реализация трейта действует везде, где видны и тип, и трейт. Варианты перечисления и их поля видны там же, где перечисление ([syn.enum.no-visibility]).

**[name.vis.private]** `private` у члена типа означает файл, где написан сам член: тело типа или блок `extend`.

**[name.vis.member]** Член виден не шире своего типа: поле с `pub` у структуры без `pub` видно только в пакете. Действующая видимость члена — более узкая из двух.

**[name.vis.tuple]** У полей структуры-обёртки (`struct UserId(Int)`) видимость не пишется ([syn.struct.form]): они видны во всём пакете — с учётом [name.vis.member].

**[name.vis.construct]** Создать значение структуры из полей — поэлементным конструктором (`Item(name = …)`, `UserId(5)`) или копией с изменениями (`p.with(y = 5.0)`) — можно только там, где видны все поля структуры. Так тип со скрытым полем создают только его собственные функции, и проверку при создании не обойти. Образец структуры может называть только видимые поля; нужно ли перечислять все поля, определяет глава 6. Как создаются значения типов стандартной библиотеки со скрытыми полями (`Box(x)`, `String()`), определяет глава 4.

**[name.vis.signature]** Объявление не может открывать менее видимое. В сигнатуре функции, в том числе функции трейта (типы параметров и результата, ограничения обобщённых параметров), в типе поля, поля варианта и константы, в псевдониме типа, в трейтах-родителях и в ассоциированном типе реализации трейта можно называть только типы и трейты, видимые везде, где видно само объявление (по [name.vis.member]). Иначе — ошибка: пользователь получил бы значение, тип которого не может назвать.

**[name.vis.lookup]** Невидимые объявления и члены в поиске не участвуют. Если поле или метод с нужным именем есть, но не виден, поиск идёт дальше — например, к методу трейта. Если не нашлось ничего, это ошибка, и компилятор называет невидимое объявление и место, где оно видно.

Два файла пакета `inventory` (пример 11-01):

```kenox
// файл src/model/item.kenox
pub struct Item {
    name: String                          // без модификатора: видно во всём пакете
    quantity: Int
    private auditTrail: List<String>      // только в этом файле

    pub fun new(name: str, quantity: Int): Item =
        Item(name = name.toString(), quantity = quantity, auditTrail = ["создан"])
}

struct Secret { code: Int }               // видна во всём пакете
// ✗ [name.vis.signature] pub fun leak(): Secret — открытая функция отдаёт тип, видимый только в пакете
```

```kenox
// файл src/main.kenox
import model.item.Item

fun main() {
    val item = Item.new("болт М6", 120)
    println(item.name)                    // ✓ тот же пакет
    // ✗ [name.vis.levels] println(item.auditTrail) — поле private: видно только в model/item.kenox
    // ✗ [name.vis.construct] val copy = Item(name = "гайка", quantity = 1, auditTrail = []) — видны не все поля
}
```

## 3.7 Члены типов и методы трейтов

**[name.member.own]** Собственные члены типа — члены из его тела и из блоков `extend Тип { … }` без трейта в том же пакете. Расширять так типы других пакетов (`extend str { … }`) — вне ядра 0.1; правила области действия для таких расширений появятся вместе с ними.

**[name.member.unique]** У собственных членов типа разные имена. Исключение — поле и функция: `x.name` всегда означает поле, а `x.name(…)` — вызов функции, поэтому поле `name`, видимое в пакете, и открытый метод `name()` для его чтения могут называться одинаково. Как вызвать значение из поля функционального типа, определяет глава 5.

**[name.trait.scope]** Метод трейта вызывается через точку (`x.area()`), а функция и константа трейта — через тип (`Int.zero()`), только если трейт в области действия модуля: объявлен в этом файле, импортирован или входит в универсальную область. Кроме того, у обобщённого параметра и его значений всегда доступны члены его трейтов-ограничений и их трейтов-родителей: `T.zero()` при `T: Zero`. Иначе метод трейта не находится, и компилятор подсказывает, какой трейт импортировать. В каком порядке ищутся свои методы, методы трейтов и расширения, определяет глава 5.

```kenox
// файл src/shapes.kenox
pub trait Shape {
    fun area(self): Float64
}

pub struct Circle { radius: Float64 }

extend Circle: Shape {
    fun area(self): Float64 = Float64.PI * self.radius * self.radius
}
```

```kenox
// файл src/main.kenox
import shapes.Circle

fun main() {
    val c = Circle(radius = 1.0)          // ✓ поле radius видно во всём пакете
    // ✗ [name.trait.scope] println(c.area()) — area — метод трейта Shape: нужен import shapes.Shape
}
```

```kenox
// файл src/report.kenox
import shapes.{Circle, Shape}

fun describe(c: Circle): String = "площадь {c.area()}"     // ✓ трейт Shape импортирован
```

## 3.8 Универсальная область

**[name.universe]** Универсальная область — внешняя для каждого модуля ([name.scope.nest]). Её имена доступны без импорта:

| Группа | Имена | Где описаны |
|---|---|---|
| Числа, логические значения, символы | `Int`, `Int8`, `Int16`, `Int32`, `Int64`, `UInt8`, `UInt16`, `UInt32`, `UInt64`, `ISize`, `USize`, `Float32`, `Float64`, `Bool`, `Char` | глава 4 |
| Текст | `str`, `String` | глава 4 |
| Особые типы | `Unit`, `Never`, `Option` | глава 4 |
| Коллекции и память | `Array`, `Slice`, `List`, `Map`, `Set`, `Box` | глава 4 |
| Результат | `Result` и его варианты `Ok`, `Err` | глава 4 |
| Сырые указатели | `RawPtr`, `RawMutPtr` | глава 9 |
| Трейты | `Copy`, `Clone`, `Drop`, `Eq`, `Order`, `Hash`, `Show`, `From`, `Iterator` | главы 4, 5 и 8 |
| Функции | `print`, `println`, `eprintln`, `panic`, `assert`, `unreachable`, `drop` | глава 10 и стандартная библиотека |

Какие из этих типов встроены в язык, а какие объявлены в стандартной библиотеке, определяет глава 4; для поиска имени разницы нет. Имена стандартной библиотеки из этой таблицы называются прелюдией.

Прелюдия минимальна: в ней имена, на которые опирается сам язык (строковые литералы и литералы коллекций, `try`, `for`, вставки в строки, владение), и самые частые функции. Добавить имя позже можно без поломки программ ([name.lookup.hide]), убрать — нельзя. Остальное импортируется: `std.ops.Add`, `std.mem.sizeOf`, `std.fs.Path`.

## 3.9 Стандартная библиотека и другие пакеты

**[name.package.std]** Стандартная библиотека — пакет-библиотека `std`. Он доступен каждому пакету без объявления зависимости, и его открытые объявления импортируются по путям `std.модуль.Имя`: `import std.fs`, `import std.collections.{Map, Set}`. Имя `std`, как и имена других пакетов, пишется только в начале пути импорта ([name.import.only]), поэтому локальная переменная `std` ничего не скрывает.

**[name.package.path]** Путь в другой пакет начинается с имени пакета. Следом идёт модуль или каталог верхнего уровня этого пакета либо открытое объявление или реэкспорт корневого модуля библиотеки: `textstats.counting.Stats`, `textstats.wordCount`. Из другого пакета видны только объявления с `pub`. В ядре 0.1 так импортируется только `std`.

**[name.package.clash]** Имя модуля или каталога верхнего уровня не может совпадать с именем пакета, к которому есть доступ: `std` или зависимости. Это ошибка: иначе начало пути импорта было бы неоднозначным.

**[name.package.root-names]** У библиотеки имя объявления или реэкспорта корневого модуля не может совпадать с именем модуля или каталога верхнего уровня — ошибка: путь `textstats.x` должен называть что-то одно.

**[name.package.deps]** Другие пакеты подключаются зависимостями в `kenox.toml`; имя зависимости — имя пакета. Зависимости — вне ядра 0.1: их формат и правила появятся вместе с пакетами (этап 4).

```text
textstats/                    name = "textstats", kind = "lib"
└── src/
    ├── lib.kenox             pub import counting.{wordCount, stats, Stats}
    └── counting.kenox        pub fun wordCount(…), pub struct Stats

inventory/src/main.kenox      import textstats.wordCount — реэкспорт корневого модуля;
                              тот же Stats доступен и как textstats.counting.Stats
```

## 3.10 Покрытие корпуса

Правила сверены с корпусом чтением: ниже — конструкции корпуса и правила, которые их описывают.

| Конструкция | Примеры | Правила |
|---|---|---|
| Модули своего пакета; импорт модуля целиком и объявления | 11-01 | [name.module.file], [name.import.path], [name.import.binds] |
| Видимость по умолчанию, `pub`, `private` | 11-01, 11-02, 03-01 | [name.vis.levels], [name.vis.private], [name.vis.member] |
| Поэлементный конструктор и проверяющая статическая функция | 03-01, 11-01, 11-02 | [name.vis.construct] |
| Реэкспорт; импорт из зависимости | 11-02, 11-01 | [name.import.reexport], [name.package.path] |
| Импорт из `std`: модуль через точку (`fs.IoError`), группы | 06-02, 09-04, 10-01, 12-01 | [name.import.path], [name.lookup.qualified] |
| Статические члены через тип: `Item.new`, `Float64.PI`, `T.zero()` | 04-01, 08-04, 11-01 | [name.lookup.qualified] |
| Поля и методы — только через `self.` | весь корпус | [name.lookup.members] |
| Трейты, объявленные в файле или в прелюдии | 04-01, 05-03, 09-04 | [name.trait.scope] |

| Привязки не повторяют видимые имена (`current` вместо `value`) | 05-02, 08-04 | [name.local.unique] |

Правки корпуса по правилам главы:

- **12-02:** `addressOf` берётся из `std.mem` — добавлен импорт; имя пакета `repr-c-demo` заменено на `repr_c_demo` ([name.package.name]).

## 3.11 Решения главы

Решения, которых не было в эскизе. Большинство следуют из эскиза и общепринятой практики; пять заметных выделены — у них есть альтернативы. Три из них разобраны в [открытых вопросах](../docs/OPEN_QUESTIONS.md) (Q-14, Q-26, Q-46). Все пять собраны в [ADR-0011](../docs/ADR/0011-modules-names-visibility.md) и утверждаются вместе с главой.

| Решение | Правило | Почему |
|---|---|---|
| Имена модулей, каталогов и пакетов — строчные латинские буквы, цифры и `_` | [name.module.name], [name.package.name] | Одинаково работают на Windows, macOS и Linux; имя пакета пишется в импорте так же, как в `kenox.toml` |
| Файл `a.kenox` рядом с каталогом `a/` — ошибка | [name.module.clash] | Путь называет либо модуль, либо каталог |
| Объявления верхнего уровня — в любом порядке; локальные — после объявления | [name.scope.module], [name.scope.local] | Как в Kotlin и Rust |
| Повтор имени обобщённого параметра во вложенном объявлении — ошибка | [name.scope.generic] | `T` метода легко спутать с `T` типа |
| Поля и методы — только через `self.`, статические члены — через тип | [name.lookup.members] | Эскиз: поля — через `self.`; параметр не спорит с полем |
| Поле и метод могут называться одинаково | [name.member.unique] | Поле, видимое в пакете, и открытый метод для его чтения — частая пара (как в Rust) |
| Три уровня видимости: файл, пакет (по умолчанию), все | [name.vis.levels] | Эскиз и ADR-0010 |
| Член не виднее типа; сигнатура не открывает менее видимое | [name.vis.member], [name.vis.signature] | Как в Kotlin и Swift: пользователь не получит тип, который не может назвать |
| Поэлементный конструктор — только где видны все поля | [name.vis.construct] | Эскиз: так строятся типы с инвариантами |
| Прелюдия минимальна; объявления модуля скрывают её без предупреждения | [name.universe], [name.lookup.hide] | Добавить имя в прелюдию можно без поломки программ, убрать — нельзя |
| Неиспользованный импорт — предупреждение; неизвестный атрибут — ошибка | [name.import.unused], [name.lookup.special] | Лишнее и опечатки видны сразу |
| **Файл — модуль, каталог — пространство имён; корневой модуль своим пакетом не импортируется** | [name.module.file], [name.module.dir], [name.module.root] | **Q-14.** Так написан корпус; зависимости идут от входа пакета к модулям, а не обратно |
| **Имена из других модулей — только через импорт; полного пути в коде нет** | [name.import.only] | Как и запрет импорта всех имён (глава 2): по импортам видно, откуда пришло каждое имя |
| **Пространство имён одно; перегрузки нет** | [name.lookup.one] | **Q-26.** Имя однозначно указывает на объявление; корпус написан без перегрузки |
| **Параметр и локальная привязка не повторяют видимое имя** | [name.local.unique] | **Q-46.** Каждое имя внутри функции означает одну переменную; ловит «хотел сравнить, а создал новую» |
| **Метод трейта — только когда трейт в области действия** | [name.trait.scope] | Эскиз, раздел 6; как в Rust: по импортам видно, какие трейты использует файл, а одноимённые методы разных трейтов не спорят |
