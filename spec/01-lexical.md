# 1. Лексика

> Глава спецификации ядра · Версия 0.1 · 5 ноября 2026 · Утверждена 05.11.2026 · Общие соглашения — [README](README.md)
>
> Лексика определяет, как текст файла делится на лексемы: идентификаторы, ключевые слова, литералы, знаки операций и переводы строк. Здесь же — правило, по которому перевод строки завершает инструкцию. Решения, которых нет в эскизе, перечислены в разделе 1.9; четыре из них утверждены отдельно 05.11.2026 (Q-42 — Q-45).

## 1.1 Исходный текст

**[lex.source.utf8]** Файл с исходным кодом имеет расширение `.kenox` и содержит текст в кодировке UTF-8. Недопустимая последовательность байтов UTF-8 — ошибка.

**[lex.source.bom]** Метка порядка байтов U+FEFF допускается только в самом начале файла и пропускается. Её добавляют некоторые редакторы на Windows.

**[lex.source.line-break]** Перевод строки — символ LF (U+000A) или пара CR LF (U+000D U+000A); пара равнозначна LF. Одиночный CR — ошибка. Поэтому один и тот же файл даёт одинаковые лексемы на Windows, Linux и macOS.

**[lex.source.whitespace]** Пробельные символы — пробел (U+0020) и табуляция (U+0009). Любой другой пробельный или невидимый символ Unicode вне строковых литералов и комментариев — ошибка: неразрывный пробел, пробел нулевой ширины и подобные символы обычно попадают в код при копировании и незаметны глазу.

**[lex.source.control]** Управляющие символы U+0000 — U+001F и U+007F — U+009F — ошибка везде, включая строки и комментарии. Исключения — табуляция, а также LF и CR в составе перевода строки. В строке их записывают экранированием (раздел 1.6.3).

**[lex.source.bidi]** Символы управления направлением текста — U+202A — U+202E и U+2066 — U+2069 — ошибка везде, включая строки и комментарии; в строке их можно записать только экранированием `\u{…}`. Эти символы меняют порядок, в котором текст показывается на экране, и позволяют спрятать код, который выглядит иначе, чем работает (атака Trojan Source, CVE-2021-42574).

```ebnf
INPUT = [ BOM ] { WHITESPACE | COMMENT | TOKEN } ;
BOM = U+FEFF ;
WHITESPACE = U+0020 | U+0009 ;
LINE_BREAK = U+000A | U+000D U+000A ;
```

## 1.2 Лексемы

**[lex.token.kinds]** Текст делится на лексемы следующих видов: идентификаторы, ключевые слова, литералы, знаки операций и пунктуации, переводы строк (`NL`) и документирующие комментарии. Пробелы и обычные комментарии разделяют лексемы и в остальном не влияют на смысл программы.

**[lex.token.longest]** В каждой позиции берётся самая длинная возможная лексема. Исключения — [lex.op.gt] и [lex.number.after-dot].

```ebnf
TOKEN = IDENT | KEYWORD | INT_LITERAL | FLOAT_LITERAL | CHAR_LITERAL
      | STRING_LITERAL | OPERATOR | DOC_COMMENT | NL ;
```

## 1.3 Комментарии

**[lex.comment.line]** Строчный комментарий начинается с `//` и продолжается до конца строки.

**[lex.comment.block]** Блочный комментарий заключён между `/*` и `*/` и может быть вложенным: `/* внешний /* внутренний */ всё ещё комментарий */`. Незакрытый блочный комментарий — ошибка.

**[lex.comment.doc]** Комментарий, который начинается ровно с трёх косых черт `///`, — документирующий: это лексема `DOC_COMMENT`, она относится к следующему объявлению. Четыре и более косых черты — обычный комментарий. Где документирующий комментарий допустим, определяет глава 2.

**[lex.comment.break]** Блочный комментарий, внутри которого есть перевод строки, действует как перевод строки (раздел 1.8); без перевода строки — как пробел.

```ebnf
COMMENT = LINE_COMMENT | BLOCK_COMMENT ;
LINE_COMMENT = ( "//" { ? любой символ, кроме перевода строки ? } ) - DOC_COMMENT ;
DOC_COMMENT = "///" [ ? любой символ, кроме "/" и перевода строки ? { ? любой символ, кроме перевода строки ? } ] ;
BLOCK_COMMENT = "/*" { BLOCK_COMMENT | ? любой символ ? } "*/" ;
```

```kenox
/// Площадь круга радиуса `r`.
fun area(r: Float64): Float64 = Float64.PI * r * r   // обычный комментарий
//// четыре черты — тоже обычный комментарий
```

## 1.4 Идентификаторы

**[lex.ident.syntax]** Идентификатор начинается с буквы или `_` и продолжается буквами, цифрами и `_` в смысле Unicode: первый символ — из множества XID_Start или `_`, остальные — из XID_Continue (UAX #31, Unicode 17.0). Ключевое слово (раздел 1.5) и одиночный `_` идентификаторами не являются.

**[lex.ident.nfc]** Идентификаторы сравниваются после нормализации Unicode NFC: два написания одного имени в разных нормальных формах — одно и то же имя.

**[lex.ident.underscore]** Одиночный `_` — отдельная лексема «заполнитель» (образцы, неиспользуемые параметры). Имя, которое начинается с `_`, например `_unused`, — обычный идентификатор.

**[lex.ident.raw]** Идентификатор в обратных кавычках — `` `type` `` — означает то же имя, что без кавычек, и допустим, даже когда имя совпадает с ключевым словом. Так записываются имена из C-библиотек и других языков. Внутри кавычек должно быть корректное написание идентификатора или ключевого слова; `` `_` ``, пробелы и переводы строк внутри — ошибка. Утверждено 05.11.2026 (Q-42).

**[lex.ident.confusable]** Компилятор предупреждает, если в одном пакете есть два разных идентификатора, которые выглядят одинаково (например, латинская `a` и кириллическая `а`), или если в одном идентификаторе смешаны письменности, которые легко спутать. Признаки похожести — по UTS #39. Предупреждение может появиться после ядра 0.1.

```ebnf
IDENT = PLAIN_IDENT | RAW_IDENT ;
PLAIN_IDENT = IDENT_CHARS - ( KEYWORD | "_" ) ;
RAW_IDENT = "`" ( IDENT_CHARS - "_" ) "`" ;
IDENT_CHARS = IDENT_START { IDENT_CONTINUE } ;
IDENT_START = ? XID_Start ? | "_" ;
IDENT_CONTINUE = ? XID_Continue ? ;
```

```kenox
val счёт = 0                  // ✓ буквы любой письменности
val _unused = 1               // ✓
val `type` = "csv"            // ✓ ключевое слово в обратных кавычках
// ✗ [lex.ident.syntax] val 1x = 0 — идентификатор не может начинаться с цифры
// ✗ [lex.ident.syntax] val type = 0 — `type` — ключевое слово
```

Стиль имён — `camelCase` для функций и переменных, `PascalCase` для типов и вариантов, `SCREAMING_CASE` для констант — не правило языка, а соглашение; за ним следит форматтер.

## 1.5 Ключевые слова

**[lex.keyword.list]** Ключевые слова не могут быть идентификаторами (кроме записи в обратных кавычках, [lex.ident.raw]):

| Назначение | Слова |
|---|---|
| Объявления | `const` `enum` `extend` `extern` `fun` `import` `private` `pub` `struct` `trait` `type` `val` `var` |
| Управление | `break` `continue` `do` `else` `for` `if` `in` `is` `loop` `match` `return` `try` `while` |
| Значения | `false` `null` `self` `Self` `true` |
| Владение и типы | `by` `consume` `dyn` `escaping` `inout` `ref` `some` `unsafe` `where` |

**[lex.keyword.reserved]** Зарезервированы на будущее и в версии 0.1 не означают ничего: `actor` `as` `async` `await` `class` `macro` `yield`. Их использование — ошибка (кроме записи в обратных кавычках).

**[lex.keyword.hard]** Все ключевые слова жёсткие: их смысл не зависит от места в программе. Утверждено 05.11.2026 (Q-42).

Не являются ключевыми словами: `it` (неявный параметр замыкания), имена типов `Int`, `String`, `Unit`, `Never`, имена `std` и `main`. Это обычные имена со своими правилами в следующих главах.

```ebnf
KEYWORD = "actor" | "as" | "async" | "await" | "break" | "by" | "class"
        | "const" | "consume" | "continue" | "do" | "dyn" | "else" | "enum"
        | "escaping" | "extend" | "extern" | "false" | "for" | "fun" | "if"
        | "import" | "in" | "inout" | "is" | "loop" | "macro" | "match"
        | "null" | "private" | "pub" | "ref" | "return" | "self" | "Self"
        | "some" | "struct" | "trait" | "true" | "try" | "type" | "unsafe"
        | "val" | "var" | "where" | "while" | "yield" ;
```

## 1.6 Литералы

### 1.6.1 Целые числа

**[lex.int.syntax]** Целый литерал — десятичный, шестнадцатеричный (`0x`), восьмеричный (`0o`) или двоичный (`0b`). Знак `_` разделяет разряды: он стоит только между двумя цифрами, по одному: `1_000_000`, `0xFF_FF`.

**[lex.int.leading-zero]** Десятичный литерал не может начинаться с нуля, если это не сам `0`: `007` — ошибка с подсказкой «восьмеричные числа пишутся как `0o7`».

**[lex.int.prefix]** Префиксы пишутся строчными буквами: `0X1F` — ошибка. Шестнадцатеричные цифры — любого регистра.

**[lex.int.boundary]** Сразу после литерала не может идти буква, цифра или `_`, не входящие в литерал: `123abc`, `0x1G`, `0b102` — ошибки. Суффиксов типа (`10u8`, `10L`) нет: тип литерала определяется по контексту (глава 4).

**[lex.int.value]** Значение литерала — целое число без ограничения величины. Помещается ли оно в свой тип, проверяет глава 4: `0xFFFF_FFFF_FFFF_FFFF` допустим для `UInt64` и ошибочен для `Int64`.

**[lex.int.sign]** Знак минус не входит в литерал: `-128` — это унарный минус, применённый к `128`. Глава 5 гарантирует, что `-128` допустим для `Int8`.

```ebnf
INT_LITERAL = DEC_LITERAL | HEX_LITERAL | OCT_LITERAL | BIN_LITERAL ;
DEC_LITERAL = "0" | NONZERO_DIGIT { [ "_" ] DEC_DIGIT } ;
HEX_LITERAL = "0x" HEX_DIGIT { [ "_" ] HEX_DIGIT } ;
OCT_LITERAL = "0o" OCT_DIGIT { [ "_" ] OCT_DIGIT } ;
BIN_LITERAL = "0b" BIN_DIGIT { [ "_" ] BIN_DIGIT } ;
DEC_DIGIT = '0' .. '9' ;
NONZERO_DIGIT = '1' .. '9' ;
HEX_DIGIT = DEC_DIGIT | 'a' .. 'f' | 'A' .. 'F' ;
OCT_DIGIT = '0' .. '7' ;
BIN_DIGIT = "0" | "1" ;
```

```kenox
val million = 1_000_000          // ✓
val mask = 0xFF                  // ✓
val flags = 0b1010_1010          // ✓
val mode = 0o755                 // ✓
// ✗ [lex.int.leading-zero] val mode = 0755 — восьмеричное число пишется как 0o755
// ✗ [lex.int.syntax] val n = 1__000 — `_` только по одному между цифрами
// ✗ [lex.int.boundary] val small = 10u8 — суффиксов нет; тип задаётся так: val small: UInt8 = 10
```

### 1.6.2 Вещественные числа

**[lex.float.syntax]** Вещественный литерал содержит дробную часть, порядок или и то, и другое: `3.14`, `1e-9`, `6.02e23`, `3.141_592_653`. Цифры обязательны с обеих сторон точки: `.5`, `5.` и `1.e3` вещественными литералами не являются.

**[lex.float.dot]** Точка относится к вещественному литералу, только если сразу за ней идёт цифра. Поэтому `1..<5` — это `1`, `..<`, `5`, а `2.pow(10)` — вызов метода у целого `2`.

**[lex.number.after-dot]** Сразу после лексемы `.` цифры образуют только десятичный целый литерал без точки, порядка и `_`: так записывается доступ к полю кортежа. `pair.0` — поле `0`; `t.0.1` — поле `1` поля `0`, а не `t` и вещественное `0.1`.

**[lex.float.value]** Значение округляется до ближайшего представимого значения своего типа (`Float64` по умолчанию; глава 4). Литерал, который не помещается в тип и округлился бы до бесконечности, — ошибка. Шестнадцатеричной записи вещественных чисел в версии 0.1 нет.

```ebnf
FLOAT_LITERAL = DEC_DIGITS "." DEC_DIGITS [ EXPONENT ] | DEC_DIGITS EXPONENT ;
DEC_DIGITS = DEC_DIGIT { [ "_" ] DEC_DIGIT } ;
EXPONENT = ( "e" | "E" ) [ "+" | "-" ] DEC_DIGITS ;
```

```kenox
val pi = 3.141_592_653          // ✓
val eps = 1e-9                  // ✓
val first = pair.0              // ✓ поле кортежа, а не вещественное число
// ✗ [lex.float.syntax] val half = .5 — нужна цифра перед точкой: 0.5
```

### 1.6.3 Символы и экранирование

**[lex.char.scalar]** Символьный литерал `'…'` содержит ровно одно скалярное значение Unicode — одну кодовую точку, а не видимую «букву» из нескольких точек. `'é'`, набранная как `e` и комбинирующий знак ударения, — ошибка с подсказкой использовать строку.

**[lex.escape.set]** Последовательности экранирования: `\n` (перевод строки), `\r`, `\t`, `\0`, `\\`, `\'`, `\"` и `\u{…}`. Другие (`\x41`, `\a`, `\{`) — ошибка. Фигурные скобки в строках записываются удвоением (раздел 1.6.4), а не экранированием.

**[lex.escape.unicode]** `\u{…}` содержит от одной до шести шестнадцатеричных цифр; значение не больше 10FFFF и не из диапазона суррогатов D800 — DFFF.

```ebnf
CHAR_LITERAL = "'" ( CHAR_CHAR | ESCAPE ) "'" ;
CHAR_CHAR = ? любой допустимый символ, кроме "'", "\" и перевода строки ? ;
ESCAPE = "\" ( "n" | "r" | "t" | "0" | "\" | "'" | '"' | UNICODE_ESCAPE ) ;
UNICODE_ESCAPE = "u{" HEX_DIGIT { HEX_DIGIT } "}" ;
```

«Допустимый символ» здесь и далее — не запрещённый правилами [lex.source.control] и [lex.source.bidi].

```kenox
val letter = 'a'                // ✓
val newline = '\n'              // ✓
val smile = '\u{1F600}'         // ✓
// ✗ [lex.escape.set] val bell = '\a' — такой последовательности нет; используйте '\u{7}'
```

### 1.6.4 Строки и вставки

**[lex.string.plain]** Обычная строка заключена в двойные кавычки и не может содержать перевод строки: для него — `\n` или многострочная строка (раздел 1.6.6).

**[lex.string.braces]** Литеральные фигурные скобки удваиваются: `{{` означает `{`, `}}` — `}`. Одиночная `}` вне вставки — ошибка.

**[lex.interp.syntax]** Одиночная `{` начинает вставку: внутри — выражение, затем, по желанию, `:` и описание формата, затем `}`. Выражение внутри вставки делится на лексемы по тем же правилам, что и остальная программа.

**[lex.interp.end]** Вставка заканчивается на первой `}`, у которой нет пары `{` внутри этой же вставки. Описание формата начинается с первой `:` вне скобок, открытых внутри вставки; `:` в составе `?:` формат не начинает. Поэтому `"{x ?: 0}"` и `"{if ok { a } else { b }}"` — вставки без формата.

**[lex.interp.nested]** Внутри вставки могут быть строковые литералы, в том числе со своими вставками: `"{names.join(", ")}"`.

**[lex.interp.single-line]** Вставка не может содержать перевод строки — и в обычной, и в многострочной строке. Длинное выражение лучше вычислить заранее.

**[lex.interp.empty]** Пустая вставка `"{}"` — ошибка с подсказкой: литеральные скобки пишутся как `{{}}`.

**[lex.interp.format]** Описание формата — текст до закрывающей `}` без `{`, `}` и переводов строк: `{x:>10}`, `{ratio:.2}`. Его смысл определяет форматирование значений в стандартной библиотеке; описание появится в главе о стандартной библиотеке.

```ebnf
STRING_LITERAL = PLAIN_STRING | RAW_STRING | MULTILINE_STRING | RAW_MULTILINE_STRING ;
PLAIN_STRING = '"' { STRING_CHAR | ESCAPE | "{{" | "}}" | INTERPOLATION } '"' ;
STRING_CHAR = ? любой допустимый символ, кроме '"', "\", "{", "}" и перевода строки ? ;
INTERPOLATION = "{" INTERP_TOKENS [ ":" FORMAT_SPEC ] "}" ;
INTERP_TOKENS = ? непустая последовательность лексем выражения без перевода строки ? ;
FORMAT_SPEC = { ? любой допустимый символ, кроме "{", "}" и перевода строки ? } ;
```

```kenox
val greeting = "Привет, {name}!"                     // ✓ вставка
val report = "итого: {total:>10}, доля: {ratio:.2}"  // ✓ вставки с форматом
val list = "{names.join(", ")}"                      // ✓ строка внутри вставки
val json = "{{\"ok\": true}}"                        // ✓ литеральные скобки
// ✗ [lex.string.braces] val s = "a } b" — одиночная `}`; литеральная скобка пишется как `}}`
// ✗ [lex.interp.empty] val s = "{}" — пустая вставка
```

### 1.6.5 Сырые строки

**[lex.raw.syntax]** Сырая строка `r"…"` не знает ни экранирования, ни вставок: `\` и фигурные скобки — обычные символы. Она не может содержать `"` и перевод строки; для текста с кавычками — многострочная сырая строка.

**[lex.raw.prefix]** Буква `r` начинает сырую строку, только если сразу за ней идёт `"` и она не продолжает идентификатор: `r"x"` — сырая строка, `ar"x"` — идентификатор `ar` и обычная строка (синтаксическая ошибка), `r "x"` — идентификатор `r` и обычная строка.

```ebnf
RAW_STRING = 'r"' { RAW_CHAR } '"' ;
RAW_CHAR = ? любой допустимый символ, кроме '"' и перевода строки ? ;
```

```kenox
val path = r"C:\Users\anna\{draft}.txt"     // ✓ без экранирования и вставок
```

### 1.6.6 Многострочные строки

**[lex.ml.open]** Многострочная строка начинается с `"""`, за которым до конца строки нет ничего, кроме пробелов и комментария.

**[lex.ml.close]** Закрывающие `"""` стоят на отдельной строке; перед ними — только пробелы и табуляции. Эти пробелы — отступ строки.

**[lex.ml.indent]** Отступ строки убирается из начала каждой строки текста при компиляции. Каждая непустая строка текста должна начинаться ровно с этого отступа — с теми же символами пробела и табуляции; строка с меньшим отступом — ошибка. Строка из одних пробелов становится пустой. Утверждено 05.11.2026 (Q-44).

**[lex.ml.edges]** Перевод строки после открывающих `"""` и перевод строки перед строкой с закрывающими `"""` в значение не входят.

**[lex.ml.content]** Внутри действуют экранирование, вставки и удвоение скобок, как в обычной строке. Кавычки `"` и `""` пишутся как есть; `"""` внутри текста записывается как `\"""`. Переводы строк в значении — всегда LF, даже если файл сохранён с CR LF.

**[lex.ml.raw]** Многострочная сырая строка `r"""…"""` устроена так же, но без экранирования и вставок; последовательность `"""` в ней невозможна.

```ebnf
MULTILINE_STRING = '"""' ML_OPENING { ML_LINE } ML_CLOSING ;
RAW_MULTILINE_STRING = 'r"""' ML_OPENING { RAW_ML_LINE } ML_CLOSING ;
ML_OPENING = { WHITESPACE } [ LINE_COMMENT ] LINE_BREAK ;
ML_LINE = { STRING_CHAR | '"' | ESCAPE | "{{" | "}}" | INTERPOLATION } LINE_BREAK ;
RAW_ML_LINE = { RAW_CHAR | '"' } LINE_BREAK ;
ML_CLOSING = { WHITESPACE } '"""' ;
```

Грамматика описывает форму строк; запрет `"""` внутри текста и отступы задают правила выше.

```kenox
fun cityJson(city: str): String {
    val json = """
        {{"city": "{city}", "ok": true}}
        """
    return json                  // значение: {"city": "…", "ok": true} без отступа и переводов строк
}
```

`true`, `false` и `null` — ключевые слова (раздел 1.5); их тип и смысл определяют главы 4 и 5.

## 1.7 Знаки операций и пунктуации

**[lex.op.list]** Знаки операций и пунктуации:

| Группа | Лексемы |
|---|---|
| Скобки | `(` `)` `[` `]` `{` `}` |
| Разделители | `,` `;` `:` `.` `@` `_` `...` |
| Присваивание | `=` `+=` `-=` `*=` `/=` `%=` `&=` `\|=` `^=` `<<=` |
| Сравнение | `==` `!=` `<` `<=` `>` |
| Арифметика | `+` `-` `*` `/` `%` |
| Логические | `&&` `\|\|` `!` |
| Битовые | `&` `\|` `^` `~` `<<` |
| Прочие | `->` `?` `?.` `?:` `..<` `..=` |

Как они комбинируются и какой у них приоритет — глава 2. Битовые операции и знак `~` утверждены 05.11.2026 (Q-43).

**[lex.op.gt]** Знак `>` всегда отдельная лексема и не сливается со следующими `>` и `=`. Операции `>=`, `>>` и `>>=` синтаксис собирает из соседних лексем без пробела между ними (глава 2). Так `List<List<Int>>` закрывает два списка аргументов типа, а `val m: Map<K, V>= …` не путается с `>=`.

**[lex.op.forbidden]** Ошибка с подсказкой — последовательности из других языков: `..` без `<`, `=` или третьей точки («диапазон пишется как `..<` или `..=`»), `::` («путь пишется через точку»), `=>` («ветка `match` пишется через `->`»). Знаки `$`, `#` и `\` вне литералов и комментариев — ошибка; для `$` подсказка — «вставка в строку пишется как `{x}`».

**[lex.op.ellipsis]** Лексема `...` допустима только в объявлении C-функции с переменным числом аргументов (ADR-0013, глава 9).

```ebnf
OPERATOR = "(" | ")" | "[" | "]" | "{" | "}" | "," | ";" | ":" | "." | "@" | "_" | "..."
         | "=" | "+=" | "-=" | "*=" | "/=" | "%=" | "&=" | "|=" | "^=" | "<<="
         | "==" | "!=" | "<" | "<=" | ">" | "+" | "-" | "*" | "/" | "%"
         | "&&" | "||" | "!" | "&" | "|" | "^" | "~" | "<<"
         | "->" | "?" | "?." | "?:" | "..<" | "..=" ;
```

```kenox
val range = 0..<10              // ✓
val nested: List<List<Int>> = [[1], [2, 3]]   // ✓ два `>` подряд
// ✗ [lex.op.forbidden] val range = 0..10 — диапазон пишется как 0..<10 или 0..=10
// ✗ [lex.op.forbidden] val fs = std::fs — путь пишется через точку: std.fs
```

## 1.8 Переводы строк и конец инструкции

Точка с запятой не нужна: перевод строки завершает инструкцию, если она закончена. Правила ниже уточняют, когда перевод строки — граница, а когда — просто пробел.

**[lex.nl.token]** Перевод строки вне строковых литералов и блочных комментариев даёт лексему `NL`. Блочный комментарий с переводом строки внутри даёт один `NL` ([lex.comment.break]).

**[lex.nl.collapse]** Несколько переводов строк подряд — в том числе разделённых только пробелами и комментариями — дают один `NL`.

**[lex.nl.brackets]** Внутри круглых `(…)` и квадратных `[…]` скобок переводы строк не дают `NL`. Решает самая внутренняя незакрытая скобка: внутри `{…}`, вложенных в круглые скобки, `NL` снова появляются — например, в теле замыкания, переданного аргументом.

**[lex.nl.semicolon]** `;` разделяет несколько инструкций в одной строке и равнозначна `NL`. Точку с запятой в конце строки форматтер удаляет.

```ebnf
NL = LINE_BREAK ;   (* появляется и пропускается по правилам этого раздела *)
```

**[lex.nl.end]** `NL` завершает текущую инструкцию, объявление или ветку `match`, если в этом месте они синтаксически закончены. Если конструкция не закончена — например, строка оборвалась на `=`, `,`, `->`, двоичной операции или открывающей скобке, — `NL` пропускается.

**[lex.nl.continue]** `NL` пропускается и тогда, когда следующая строка начинается с лексемы продолжения: `.` `?.` `?:` `&&` `||` `==` `!=` `<` `<=` `>` `+` `*` `/` `%` `|` `^` `<<` `..<` `..=` `->` или ключевых слов `else`, `where`, `by`, `is`. Эти лексемы не могут начинать инструкцию, поэтому такая строка продолжает предыдущую. Лексемы `-`, `!`, `&`, `~`, `(`, `[`, `{` и `@` могут начинать инструкцию — строка, которая начинается с них, начинает новую инструкцию.

**[lex.nl.match-arm]** Исключение: на уровне веток `match` — непосредственно внутри фигурных скобок `match` — `NL`, за которым идёт `.`, начинает новую ветку, а не продолжает предыдущую: так пишутся образцы `.Вариант`. Многострочную цепочку методов в теле ветки заключают в круглые скобки или в блок. Утверждено 05.11.2026 (Q-45).

```kenox
fun total(items: Slice<Item>): Int =
    items.iter()
        .filter { it.price > 0 }
        .map { it.price }
        .sum()                                  // ✓ строки начинаются с точки — это продолжение

fun valid(a: Int, b: Int): Bool {
    val both = a > 0 &&
        b > 0                                   // ✓ строка оборвалась на &&
    val either = a > 0
        || b > 0                                // ✓ строка начинается с ||
    return both || either
}

fun area(shape: Shape): Float64 = match shape {
    .Circle(r) -> Float64.PI * r * r
    .Square(a) -> (a.toFloat64()
        .pow(2))                                // ✓ цепочка в ветке — в скобках
    .Empty -> 0.0                               // ✓ новая ветка
}
```

```kenox
// ✗ [lex.nl.match-arm] `.sqrt()` здесь начинает новую ветку, а не продолжает цепочку:
// match shape {
//     .Circle(r) -> r.toFloat64()
//         .sqrt()
// }
```

Следствие: инструкция внутри блока не может начинаться с `.Вариант` — такая строка продолжила бы предыдущую. Значение варианта в начале строки заключают в скобки: `(.Empty)`. Строка, которая начинается с `-`, начинает новую инструкцию: `a` и `- b` на разных строках — это две инструкции, и компилятор предупредит, что значение `-b` не используется.
